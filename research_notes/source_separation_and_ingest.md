# Music Source Separation Tools and YouTube Audio Acquisition for a Python Pipeline (status as of 2026-10-01)

Scope: (1) obtaining audio + metadata from a YouTube video in Python, (2) open-source and commercial stem-separation tools for rock/pop (guitar, keys, bass, vocals, drums), benchmarks, practicalities on Windows 11 + consumer NVIDIA GPU, and whether separation helps downstream chord/note transcription. All dates are as stated in the cited sources; research conducted 2026-10-01.

## Key Question 1: YouTube ingest with yt-dlp (status, ffmpeg, flags, PO tokens / cookies / JS runtime in 2025-2026)

### Takeaway
yt-dlp remains the de-facto tool and is actively maintained, but in 2025-2026 a working YouTube setup is no longer "pip install yt-dlp": it now needs (a) ffmpeg for audio extraction, (b) an external JavaScript runtime (Deno recommended) plus the `yt-dlp-ejs` package, and (c) for some clients, a Proof-of-Origin (PO) token provider plugin. Cookies and PO tokens solve different problems and one does not substitute for the other.

### Cited Findings
- yt-dlp requires Python 3.10+ (CPython) / 3.11+ (PyPy); ffmpeg is "required for merging separate video and audio files" and for post-processing; `-x/--extract-audio` with `--audio-format` supporting "best (default), aac, alac, flac, m4a, mp3, opus, vorbis, wav"; YouTube support "requires yt-dlp-ejs and a JavaScript runtime (deno recommended)"; `--cookies-from-browser` supports Chrome, Firefox, Safari and others; licensed under the Unlicense (bundled executables may include GPLv3+ code from PyInstaller). Repository shows ~195k stars and ~24,000 commits, i.e. actively developed. — [yt-dlp GitHub README](https://github.com/yt-dlp/yt-dlp)
- yt-dlp must "solve JavaScript challenges presented by YouTube using an external JavaScript runtime"; EJS replaces the older JSInterp/PhantomJS approaches. Supported runtimes: Deno (recommended, enabled by default, min v2.3.0); Node (min v22.0.0, needs `--js-runtimes node`); QuickJS/QuickJS-NG (min 2023-12-9); Bun (deprecated, up to 1.3.14). For pip installs use `pip install -U "yt-dlp[default]"` ("The default dependency group includes the yt-dlp-ejs package"); if installing `yt-dlp-ejs` separately its version "MUST match the version specified in yt-dlp's pyproject.toml". — [yt-dlp wiki: EJS](https://github.com/yt-dlp/yt-dlp/wiki/EJS)
- A PO Token "is generated by an attestation provider on Web, Android and iOS platforms to attest the requests are coming from a genuine client." The wiki's enforcement table says a GVS (streaming) PO token is required for clients mweb, web, web_safari, tv_simply, web_music, web_creator, android, ios; not required for web_embedded, android_vr, tv; and "GVS PO Token is not required for YouTube Premium subscribers". Two featured provider plugins: `bgutil-ytdlp-pot-provider` ("Maintained by a yt-dlp maintainer") and `yt-dlp-getpot-wpc` (browser-based generation, "Maintained by a yt-dlp core maintainer"). Page last edited 2026-07-12. — [yt-dlp wiki: PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)
- "Cookies prove who you are. A PO token proves where the request came from. Supplying one does nothing for the other." The bgutil helper "generates tokens on demand and the main yt-dlp call picks them up automatically." (third-party blog, undated beyond "2025-2026") — [renderio.dev: Why yt-dlp keeps breaking](https://renderio.dev/blogs/ytdlp-geo-block-pot-cookies)
- Open issue (2026): members-only downloads fail with cookies unless a PO Token provider is configured — illustrates that cookies alone are insufficient for some content. — [yt-dlp issue #17644](https://github.com/yt-dlp/yt-dlp/issues/17644)
- YouTube audio-only formats as exposed by yt-dlp: format 140 = m4a/AAC ~130 kbps 44.1 kHz; format 251 = webm/Opus ~110 kbps 48 kHz; `bestaudio` (`ba`) picks the best audio-only format; `bestaudio[ext=m4a]` or `bestaudio[acodec=opus]` select a codec. — [The Spacebar: yt-dlp audio-only](https://www.spacebar.news/how-to-download-audio-only-media-files-with-yt-dlp/) (consistent with the format list in [yt-dlp README](https://github.com/yt-dlp/yt-dlp))
- `--write-info-json` writes a JSON sidecar of all metadata; `--embed-metadata` embeds metadata into the output file; output-template fields include `title`, `artist`, `album`, `uploader`, `channel`. — [yt-dlp GitHub README](https://github.com/yt-dlp/yt-dlp)

### Inferences
- For a transcription pipeline, do not transcode to MP3: use `-f bestaudio -x --audio-format wav` (or keep the native Opus/AAC and decode with ffmpeg in-process) so separation models receive an uncompressed 44.1/48 kHz input. YouTube source audio is itself lossy (~110-130 kbps), so there is no benefit beyond that; FLAC/WAV output simply avoids a second lossy generation.
- Practical Windows 11 install set: `pip install -U "yt-dlp[default]"`, a static ffmpeg build on PATH (yt-dlp publishes its own FFmpeg-Builds), Deno installed on PATH, and optionally `bgutil-ytdlp-pot-provider` if the default client set starts failing with "PO token required" messages. Public, non-age-restricted videos frequently still work without a PO token because yt-dlp falls back to clients that don't require one (web_embedded, android_vr, tv per the wiki table), but this is version- and time-dependent.
- Using `--cookies-from-browser` with your main Google account is the documented way to access age-restricted/members content; the PO Token Guide itself contains no explicit ban warning, but it is a logged-in account doing automated access, which the YouTube ToS prohibits (see Question 3).

### Gaps
- Which yt-dlp release first required the JS runtime / yt-dlp-ejs is not stated in the EJS wiki page; the exact current version number was not visible in the fetched README.
- No primary source gives a definitive rule for when audio-only downloads of ordinary public videos require a PO token in late 2026; the wiki table is per-client and the default client list changes with releases.

## Key Question 2: pytube / pytubefix alternatives and obtaining official title/artist metadata

### Takeaway
pytubefix is an actively maintained pure-Python alternative that can download audio-only streams and supports OAuth for restricted content, but it is a smaller project than yt-dlp; yt-dlp's `--write-info-json`/`extract_info` output is the most complete metadata source (title, uploader, channel, and `artist`/`track`/`album` fields when YouTube supplies them).

### Cited Findings
- pytubefix shows active development (1,058 commits, ~1.6k stars); audio-only download via `yt.streams.get_audio_only()` returning `.m4a`; metadata properties include `title`, `author`, `views`, `likes`, `thumbnail_url`; restricted content handled via `use_oauth=True` / `allow_oauth_cache=True` ("Authenticate once for subsequent downloads"). The README content fetched contained no mention of PO tokens or a Node.js requirement. — [pytubefix GitHub](https://github.com/JuanBindez/pytubefix)
- yt-dlp exposes `title`, `artist`, `album`, `uploader`, `channel` as output-template fields and can write them to a sidecar via `--write-info-json` or embed via `--embed-metadata`. — [yt-dlp GitHub README](https://github.com/yt-dlp/yt-dlp)
- YouTube Music streams: Opus averages ~140 kbps VBR; AAC-LC/M4A is 128 kbps CBR. — [YTMusicDL project README via search](https://github.com/RaduTek/YTMusicDL)

### Inferences
- In Python, calling `yt_dlp.YoutubeDL({...}).extract_info(url, download=True)` returns the same dict as `--write-info-json`; `artist`, `track`, `album` keys are only populated for videos YouTube tags as music (official uploads / "Music in this video" / YouTube Music), otherwise fall back to parsing `title` and `uploader`/`channel` (e.g. "Artist - Title (Official Video)").
- pytubefix is a reasonable fallback when yt-dlp is broken on a given day, but because it does not document PO-token handling it is likely to fail on the same bot-detection changes.

### Gaps
- I did not find a primary statement on the status of the original `pytube` project in 2026 (the pytubefix README fetched did not describe it); its name alone (a "fix" fork) implies pytube was unmaintained, but this is not sourced.
- Exact pytubefix release version/date was not visible in the fetched page.

## Key Question 3: Legal considerations (YouTube ToS, personal use)

### Takeaway
YouTube's Terms of Service (effective 2025-03-17) expressly prohibit downloading or accessing content except as permitted by the Service, with YouTube's written permission, or "as permitted by applicable law"; downloading for a personal transcription tool is therefore a ToS breach even if it may be lawful in some jurisdictions. This is a summary of the ToS text, not legal advice.

### Cited Findings
- Effective date 2025-03-17. "You are not allowed to: access, reproduce, download, distribute, transmit, broadcast, display, sell, license, alter, modify or otherwise use any part of the Service or any Content except: (a) as specifically permitted by the Service; (b) with prior written permission from YouTube and, if applicable, the respective rights holders; or (c) as permitted by applicable law". The terms permit viewing/listening "for personal, non-commercial purposes" and embedding via the official player; they prohibit automated access tools. — [YouTube Terms of Service](https://www.youtube.com/t/terms)
- yt-dlp code is released under the Unlicense (public domain-equivalent); the tool itself is legal to distribute, independent of how it is used. — [yt-dlp GitHub README](https://github.com/yt-dlp/yt-dlp)

### Inferences
- The ToS carve-out "(c) as permitted by applicable law" is the only hook for private-copy/personal-use arguments; whether that applies depends on the user's jurisdiction (e.g. private copying exceptions in some EU states vs. none in the UK/US for this scenario). Separation and transcription of a downloaded track also implicate the underlying musical-work copyright for anything beyond personal study.
- Operationally, the lower-risk path is to download only content the user has rights to or for strictly personal practice use, avoid logged-in cookies (reduces account risk), and never redistribute downloaded audio or stems.

### Gaps
- No case law or official YouTube enforcement statements specific to personal-use downloading for transcription were found; the general press claim that yt-dlp "is legal to use but ToS-violating on YouTube" appears in secondary guides (e.g. [plisio yt-dlp guide 2026](https://plisio.net/cybersecurity/yt-dlp)) rather than in primary sources.

## Key Question 4: Separation models — Demucs v4 (incl. htdemucs_6s), UVR/MDX-Net/MDX23, BS-/Mel-Band RoFormer, audio-separator, Spleeter, Open-Unmix, LarsNet, and guitar-specific / lead-vs-rhythm models

### Takeaway
As of 2026 the quality frontier for open weights is RoFormer-family models (BS-RoFormer / Mel-Band RoFormer) run through `python-audio-separator` or ZFTurbo's MSST framework; Demucs v4 (`htdemucs_ft`) remains a solid, MIT-licensed, easy-to-install 4-stem baseline but the repo was archived on 2025-01-01, and its 6-stem variant's guitar stem is "okay" and piano stem is poor. The strongest 6-stem (incl. guitar + piano) model available as downloadable weights is "BS Roformer SW" (guitar SDR ~9.0 on MVSEP's leaderboard vs ~7.0 for the best earlier open guitar model), but its weights have no stated license or provenance. Lead-vs-rhythm guitar separation exists only as commercial/hosted services (Moises/Music.ai since April 2024; MVSEP since March 2026); no open-weights lead/rhythm model was found.

### Cited Findings

**Demucs v4 (Meta / Alexandre Défossez)**
- Repository archived "as of January 1, 2025"; maintainer note: "As I am no longer working at Meta, this repository is not maintained anymore." A community fork exists at github.com/adefossez/demucs "with limited activity". Models: `htdemucs` (default, Hybrid Transformer v4, 9.0 dB SDR on MUSDB18-HQ), `htdemucs_ft` (fine-tuned, same 9.0 dB listing, "4x slower"), `htdemucs_6s` (adds guitar/piano: "okay quality for guitar, but a lot of bleeding and artifacts for the piano source"), `hdemucs_mmi` (v3 baseline), `mdx_extra` (won MDX challenge track B). MIT license. Python 3.8+. GPU memory minimum 3 GB, 7 GB recommended; `--segment 8` to reduce memory; Hybrid Transformer models have a maximum segment length of 7.8 s. CPU: roughly "1.5 times the duration of the track". Install: `python3 -m pip install -U demucs`. — [facebookresearch/demucs README](https://github.com/facebookresearch/demucs)
- MVSEP's description of Demucs4 HT 6-stem: the two extra stems "piano" and "guitar" have quality that "is still so-so". — [MVSEP algorithms page](https://mvsep.com/en/algorithms)
- Anecdotal user report (Hacker News, Feb 2025): "The dedicated guitar and piano stems are usually full of really bad artifacts in the 6s model"; prefers the 4-stem model. — [Hacker News comment](https://news.ycombinator.com/item?id=42994276)
- MSST's pretrained table lists HTDemucs4 (4-stem) at avg SDR 9.16 (bass 11.76, drums 10.88, vocals 8.24, other 5.74) and HTDemucs4 FT single-stem models at drums 11.13 / bass 11.96 (on MUSDB18HQ or MVSEP Multisong as noted per row). — [MSST docs/pretrained_models.md](https://github.com/ZFTurbo/Music-Source-Separation-Training/blob/main/docs/pretrained_models.md)
- Runtime reports: htdemucs_ft on a 4-minute song on an RTX 3090 "takes 24 seconds" (third-party blog, 2026) — [dev.to: Spleeter is dead](https://dev.to/stevecase430/spleeter-is-dead-heres-why-everyones-switching-to-demucs-in-2026-j6e); a 6:24 FLAC on an RTX 3060 Ti took 15.6 s on GPU vs 187.8 s CPU-only — [LinuxLinks Demucs review](https://www.linuxlinks.com/machine-learning-linux-demucs-music-source-separation/2/).

**Ultimate Vocal Remover (UVR) / MDX-Net / MDX23**
- Latest tagged UVR GUI release is v5.6 (2023-09-26) with a Windows 10+ installer; release notes describe a "Beta Roformer (and DirectML) Version of UVR" that adds "the ability to run Roformer, SCnet, & Bandit Models" via the Download Center. — [UVR releases](https://github.com/anjok07/ultimatevocalremovergui/releases)
- audio-separator (the pip-installable port of UVR's inference) default model is `model_bs_roformer_ep_317_sdr_12.9755.ckpt` (vocal SDR 12.9); supports MDX (ONNX), VR (.pth), Demucs (YAML, 4 or 6 stems), and MDXC/RoFormer (.ckpt/YAML). — [python-audio-separator README](https://github.com/nomadkaraoke/python-audio-separator)
- Maintainer's model guidance (Oct 2024): instrumental/vocals: `model_bs_roformer_ep_317_sdr_12.9755.ckpt` (vocals 12.9 / instrumental 17.0), `MDX23C-8KFFT-InstVoc_HQ_2.ckpt` (12.2 / 16.3); individual instrument stems: `htdemucs_6s.yaml` (drums 8.5, bass 10.0), `kuielab_a_bass.onnx`, `kuielab_a_drums.onnx`; models credited to Aufr33, Viperx, Kimberley Jensen, unwa. — [audio-separator discussion #133](https://github.com/nomadkaraoke/python-audio-separator/discussions/133)
- SDX 2023 Music Demixing track: top score SAMI-ByteDance, average SDR 9.97 dB on the Standard leaderboard; LabelNoise: CCOM 7.46 dB; Bleeding: kuielab 6.58 dB. — [SDX23 Music Demixing Track (TISMIR)](https://transactions.ismir.net/articles/10.5334/tismir.172); [arXiv 2308.06979](https://arxiv.org/abs/2308.06979)

**BS-RoFormer / Mel-Band RoFormer**
- BS-RoFormer (ByteDance): pure-Transformer band-split with RoPE; the system trained on MUSDB18HQ + 500 extra songs "ranked first place in the MSS track of Sound Demixing Challenge (SDX23)"; a smaller version reaches 9.80 dB average SDR on MUSDB18HQ without extra data. — [arXiv 2309.02612](https://arxiv.org/abs/2309.02612)
- Mel-Band RoFormer maps frequency bins into overlapped mel-scale subbands and "outperforms BS-RoFormer in the separation tasks of vocals, drums, and other stems using the MUSDB18HQ dataset." — [Mel-Band RoFormer (CatalyzeX summary of arXiv paper)](https://www.catalyzex.com/paper/mel-band-roformer-for-music-source-separation)
- MSST pretrained table: BS Roformer (viperx) vocals 10.87 (another viperx BS-RoFormer vocal variant listed at 12.97 elsewhere), MelBand Roformer (KimberleyJensen) vocals 10.98, BS PolarFormer vocals 11.00, SCNet XL IHF 4-stem avg 9.92, BS Roformer (viperx) "other" 6.85. — [MSST docs/pretrained_models.md](https://github.com/ZFTurbo/Music-Source-Separation-Training/blob/main/docs/pretrained_models.md); [AEmotionStudio/roformer-models HF card](https://huggingface.co/AEmotionStudio/roformer-models)
- MVSEP (Jan 2025): "weights obtained on the MUSDB18 dataset have been published for the top models BSRoformer, MelBandRoformer and SCNet XL" via GitHub releases. — [MVSEP news](https://mvsep.com/en/news)
- "BS Roformer SW" 6-stem model (vocals, bass, drums, guitar, piano, other) became MVSEP's default for new users in Sept 2025; MVSEP-reported metrics: vocals 11.30, instrumental 17.50, bass 14.62, drums 14.11, guitar 9.05, piano 7.83, other 8.71 (these are on MVSEP's own evaluation set, not MUSDB18). — [MVSEP news](https://mvsep.com/en/news); [MVSEP algorithms](https://mvsep.com/en/algorithms)
- MVSEP Guitar leaderboard (top entries): #1 "BS Roformer SW (UVR5.6)" guitar SDR 9.012; #2 "Logic Pro 11.2 Stem Splitter by Apple Inc." 9.002; #3 bs_6stem_guitar0920 8.985; #8 sami-bytedance-v.1.2 8.277; "MVSep Guitar MelBand Roformer (2024.06.25)" is #17 at 7.021. No entry named htdemucs_6s/Demucs/MDX23C appears in the top 20 shown. — [MVSEP guitar leaderboard](https://mvsep.com/quality_checker/leaderboard/guitar)
- BS-RoFormer-SW 6-stem weights are circulating as community re-exports: an ONNX export (fp16 336 MB, fp32 669 MB; stems bass, drums, other, vocals, guitar, piano; 44.1 kHz; fixed 4-second (176,400-sample) chunks because "the model's rotary embedding caches by sequence length") states the original weights were "rehosted by jarredou" with no stated license and the exporter has "no provenance information" about training; the export code is MIT. — [elicwhite/bs-roformer-sw-6stem-onnx on Hugging Face](https://huggingface.co/elicwhite/bs-roformer-sw-6stem-onnx); a GGUF re-export also exists — [studio409/BSRoformer-SW-6Stem-GGUF](https://huggingface.co/studio409/BSRoformer-SW-6Stem-GGUF)
- MSST (Music-Source-Separation-Training, ZFTurbo): MIT-licensed framework supporting 19+ architectures (MDX23C, Demucs4HT, BS/Mel-Band RoFormer, SCNet, BandIt, Apollo, BSMamba2, Conformer, DTTNet, etc.); inference via `python inference.py --model_type ... --config_path ... --start_check_point ...`; configs tuned for an "NVIDIA A6000 48GB" with guidance to reduce batch size. — [ZFTurbo/Music-Source-Separation-Training](https://github.com/ZFTurbo/Music-Source-Separation-Training); companion paper submitted 2026-07-25 — [arXiv 2607.23395](https://arxiv.org/abs/2607.23395)
- Lightweight MIT inference wrappers for single RoFormer checkpoints: `bs-roformer-infer` and `melband-roformer-infer` on PyPI (openmirlab). — [bs-roformer-infer PyPI](https://pypi.org/project/bs-roformer-infer/); [melband-roformer-infer GitHub](https://github.com/openmirlab/melband-roformer-infer)

**Spleeter, Open-Unmix, LarsNet**
- Spleeter (Deezer): MIT; 2/4/5-stem models (5-stem adds piano); TensorFlow-based; latest PyPI release 2.4.2 on 2025-04-03; README warns 2.1.0 dropped the dedicated GPU package and that conda is no longer recommended; a commercial "Spleeter Pro" is advertised. — [deezer/spleeter](https://github.com/deezer/spleeter); [spleeter on PyPI](https://pypi.org/project/spleeter/)
- Open-Unmix (sigsep): 4-stem reference implementation; "remains lightly maintained, having been updated for Torch 2.0 in 2024." — [sigsep/open-unmix-pytorch](https://github.com/sigsep/open-unmix-pytorch)
- LarsNet (Politecnico di Milano): separates a stereo drum mix into kick, snare, toms, hi-hat, cymbals using a bank of U-Nets, "up to 62.5 times faster than real-time"; also shipped as an open-source VST3 ("LARS"). — [arXiv 2312.09663](https://arxiv.org/pdf/2312.09663)

**Guitar-specific and lead-vs-rhythm**
- Moises (2024-04-24) announced "Lead & Rhythm Guitar" and "Acoustic & Electric Guitar" separation (6 total tracks with vocals/bass/drums/other), describing the lead/rhythm model as "the first-ever model that accurately separates lead and rhythm guitars"; available to Premium and Pro users, Pro gets "Hi-Fi separation". — [Moises blog](https://moises.ai/blog/moises-news/new-guitar-separation-models/)
- Music.ai (Moises' API) lists "Guitar parts (Rhythm, Solo)" at $0.10/min, "Guitar stems (Acoustic, Electric)" $0.10/min, "Musical stems (Vocals, Bass, Drums, Guitars, Keys, Piano, Strings, Wind)" $0.07/min, "Drum stems (Kick, Snare, Toms, Hi-hat, Cymbals)" $0.15/min, "Chords recognition" $0.04/min, pay-as-you-go with 2 concurrent jobs and 48 h storage. — [Music.ai pricing](https://music.ai/pricing/); [Music.ai Guitar Parts module](https://music.ai/modules/stem-separation/guitar-parts/)
- MVSEP (2026-03-21) added 12 specialized models including "MVSep Lead/Rhythm Guitar (sep_type=101)", Plucked Strings, Keys, Percussion, Brass, Woodwind, Choir, FX; the announcement gives no architecture or SDR, and no open weights are mentioned. — [MVSEP news](https://mvsep.com/en/news)
- MVSep Guitar (guitar vs. everything else) is "based on the MDX23C, Mel Roformer and BSRoformer architectures" and covers acoustic and electric guitar. — [MVSEP algorithm 17](https://mvsep.com/algorithms/17)
- LALAL.AI (2026-09-03) added a unified "Guitars" stem (acoustic + electric + processed guitars in one output, claimed ~20% fewer classification errors than separate acoustic/electric stems) and rebuilt its Piano stem on the "Andromeda" architecture; both exposed via REST API; Guitars is cloud-only. — [KVR Audio news](https://www.kvraudio.com/news/lalal-ai-adds-guitars-and-piano-stems-to-andromeda-model-68357)
- Research datasets relevant to guitar separation/transcription: GuitarDuets (classical guitar duet separation, 2025) — [arXiv 2507.01172](https://arxiv.org/abs/2507.01172); Guitar-TECHS electric-guitar dataset (2025) — [ResearchGate](https://www.researchgate.net/publication/390536875_Guitar-TECHS_An_Electric_Guitar_Dataset_Covering_Techniques_Musical_Excerpts_Chords_and_Scales_Using_a_Diverse_Array_of_Hardware).
- Steinberg SpectraLayers 12 Pro is discussed by users as a manual/semi-automatic route to split lead from rhythm guitar (forum thread; no benchmark). — [Steinberg forums](https://forums.steinberg.net/t/sl12-pro-for-splitting-lead-rhythm-guitar-advice-and-sourcing-video-tutorials/1015919)

### Inferences
- Recommended open stack for the pipeline: `python-audio-separator[gpu]` as the runtime, with (a) `htdemucs_ft` or a 4-stem RoFormer/SCNet model for vocals/drums/bass/other, and (b) BS-RoFormer-SW 6-stem for a guitar and piano stem when needed, keeping `htdemucs_6s` only as a fully-licensed (MIT) fallback. The ~2 dB guitar-SDR gap between BS-Roformer-SW (~9.0) and the 2024 Mel-RoFormer guitar model (~7.0) on the same MVSEP leaderboard is large by MSS standards.
- Lead vs. rhythm guitar: for a Python pipeline the only options in 2026 are API calls (Music.ai at $0.10/min, LALAL.AI, MVSEP) — treat as an optional paid stage. For the stated ukulele-tab goal, a single "guitar" stem plus the "other" stem is likely sufficient for chord recognition; lead/rhythm matters only for melody-line transcription.
- Piano/keys is the weakest stem across all open models (htdemucs_6s "bleeding and artifacts"; BS-Roformer-SW piano 7.83 vs guitar 9.05 on MVSEP's set), so chord estimation on a piano stem will be less reliable than on guitar/bass.
- "Spleeter is dead" is a widespread blog framing, but the repo did publish 2.4.2 in April 2025; it is better characterized as maintenance-only with 2019-era quality (no RoFormer/Transformer models) and a TensorFlow dependency that is awkward on Windows next to PyTorch. Nothing in the fetched README called it deprecated.

### Gaps
- No MUSDB18-HQ per-stem SDR for `htdemucs_6s` guitar/piano is published by Meta (MUSDB18 has no guitar/piano ground truth); only qualitative statements exist.
- The training provenance and license of the BS-Roformer-SW 6-stem checkpoint are unknown (explicitly stated by the HF re-exporter). The MVSEP leaderboard labels it "(UVR5.6)", suggesting it ships via the UVR Download Center, but I could not confirm an official UVR/Anjok07 release note or license text for it.
- No per-stem SDR or architecture details for MVSEP's Lead/Rhythm Guitar model (March 2026) or for Moises' lead/rhythm model were published.
- Gaudio (Gaudio Lab) commercial API: no sources were retrieved in this research; status unknown.
- Dates of individual MVSEP leaderboard entries were not shown on the fetched page.

## Key Question 5: Benchmarks (MUSDB18-HQ SDR per stem, SDX 2023) and what SDR means for downstream transcription

### Takeaway
On MUSDB18-HQ, average 4-stem SDR progressed from ~9.0 dB (Demucs v4, 2022) to ~9.8-10.0 dB (BS-RoFormer small / SDX23 winner, 2023) and ~9.9 dB (SCNet XL in MSST's table); vocals and bass/drums are consistently the best-separated stems while "other" (where guitar and keys live in 4-stem models) is the worst at ~6-7 dB. For transcription, SDR is a proxy only: separation artifacts, not SDR alone, drive downstream errors, and the few empirical studies found show both gains and losses.

### Cited Findings
- Demucs v4 `htdemucs`/`htdemucs_ft`: 9.0 dB average SDR on MUSDB18-HQ. — [facebookresearch/demucs](https://github.com/facebookresearch/demucs)
- HTDemucs4 per-stem (MSST evaluation): bass 11.76, drums 10.88, vocals 8.24, other 5.74, avg 9.16; SCNet XL IHF avg 9.92; Demucs3 mmi avg 8.88. — [MSST pretrained models table](https://github.com/ZFTurbo/Music-Source-Separation-Training/blob/main/docs/pretrained_models.md)
- BS-RoFormer small: 9.80 dB avg on MUSDB18HQ without extra data; full system 1st in SDX23 MSS track. — [arXiv 2309.02612](https://arxiv.org/abs/2309.02612)
- SDX23 Music Demixing: winner SAMI-ByteDance 9.97 dB avg SDR (Standard leaderboard). — [TISMIR SDX23 paper](https://transactions.ismir.net/articles/10.5334/tismir.172)
- Third-party 2026 comparison puts Demucs v4 at 9.00-9.20 dB vs BS-RoFormer small 9.80 dB and calls RoFormer "the most computationally heavy" and "most VRAM-hungry" of MDX-Net/Demucs/RoFormer, while noting "no unified official benchmark exists" for VRAM/speed. — [tomodahinata BS-RoFormer guide (2026-06-25, updated 2026-07-23)](https://tomodahinata.com/en/blog/bs-roformer-mel-band-roformer-vocal-separation-guide)
- MVSEP's "Benchmarks and leaderboards for sound demixing tasks" paper describes its MultiSong evaluation set and ensemble SDRs used by the MVSEP quality checker. — [arXiv 2305.07489](https://arxiv.org/html/2305.07489v2)
- Guitar-specific: MVSEP's September 2024 guitar ensemble reached SDR 7.18 on its guitar leaderboard; "MelRoformer (2024.06, SDR: 7.02)" beat the older MDX23C guitar model (6.34). Piano: SCNet Large 5.89, ensemble 6.19 (Sept 2024); earlier MDX23C piano 4.92-7.27 depending on validation subset (Sept 2023). — [MVSEP news](https://mvsep.com/en/news)
- Guitar string separation (Wave-U-Net, GuitarSet/DadaGP-derived datasets): "source separation improves transcription performance in comparison to the original soundtrack, though performance is still sub-optimal due to artifacts" (IEEE TASLP, Jan 2025). — [Separate and Transcribe (IEEE Xplore)](https://ieeexplore.ieee.org/document/11179987/)

### Inferences
- Guitar (~9 dB on MVSEP's set) and bass (~12-14.6 dB) stems are now good enough that monophonic/bass-line pitch tracking should be reliable; piano (~6-8 dB) and "other" (~6-9 dB) are the stems where chord-estimation bleed from vocals/synths is still a real risk.
- MVSEP numbers and MUSDB18-HQ numbers are not comparable (different test sets; MVSEP's SDRs are generally several dB higher for the same model class, e.g. bass 14.62 vs ~12).

### Gaps
- No published per-stem MUSDB18-HQ results for guitar or piano exist because MUSDB18 lacks those labels; all guitar/piano SDRs are on private or MVSEP datasets.
- I found no study that maps SDR thresholds to chord-recognition or note-transcription accuracy.

## Key Question 6: Practicalities — GPU VRAM, CPU runtime, Windows 11 install, PyTorch versions, model sizes, licensing

### Takeaway
Demucs v4 needs ~3-7 GB VRAM and runs a 4-minute song in roughly 15-45 s on a mid/high consumer RTX GPU or ~1.5x-real-time-plus on CPU; RoFormer models are heavier (no official numbers) and are best run via `audio-separator[gpu]` (PyTorch 2.3+, onnxruntime-gpu, CUDA 11.8/12.2, ffmpeg). Code is MIT across Demucs, audio-separator, MSST and the RoFormer reference implementations, but checkpoint licenses vary: Kimberley Jensen's Mel-Band RoFormer is MIT, some UVR-era MDX models have unclear terms, and BS-RoFormer-SW has none stated.

### Cited Findings
- Demucs: "Minimum 3GB; 7GB recommended" GPU memory; `--segment 8` lowers memory; CPU ~1.5x track duration; Python 3.8+; Windows install guidance in repo docs. — [facebookresearch/demucs](https://github.com/facebookresearch/demucs)
- GPU timings: RTX 3090 htdemucs_ft 24 s / 4-min song — [dev.to 2026](https://dev.to/stevecase430/spleeter-is-dead-heres-why-everyones-switching-to-demucs-in-2026-j6e); RTX 3060 Ti 15.6 s vs CPU 187.8 s for a 6:24 track — [LinuxLinks](https://www.linuxlinks.com/machine-learning-linux-demucs-music-source-separation/2/); other blogs estimate RTX 3080 ~45 s, RTX 4090 ~30 s, "modern i7" CPU 8-15 min for 4 min — [stemsplit.io setup guide](https://stemsplit.io/blog/demucs-local-setup-guide) (third-party estimates, not measured benchmarks).
- audio-separator install: `pip install "audio-separator[cpu]"` or `"audio-separator[gpu]"` (CUDA) or `"audio-separator[dml]"` with `--use_directml` for AMD/Intel on Windows (experimental); requires PyTorch 2.3+, onnxruntime-gpu for CUDA, supported CUDA 11.8 and 12.2, FFmpeg for I/O; `--chunk_duration 600` to avoid OOM on long files; memory "scales with segment size and batch size"; `audio-separator --list_models` shows SDR per model; Python API `Separator().load_model(model_filename=...)`, `separate([...])`. MIT; "If integrating the default UVR models, please honor the MIT license by providing credit to UVR and its developers." — [python-audio-separator README](https://github.com/nomadkaraoke/python-audio-separator)
- BS-RoFormer-SW 6-stem ONNX sizes: 336 MB fp16, 669 MB fp32. — [HF elicwhite](https://huggingface.co/elicwhite/bs-roformer-sw-6stem-onnx)
- MSST training configs assume an A6000 48 GB (training, not inference) and advise reducing batch size for smaller GPUs. — [ZFTurbo MSST](https://github.com/ZFTurbo/Music-Source-Separation-Training)
- Licensing: Kimberley Jensen released the Mel-Band RoFormer model under MIT (April); her earlier Kim_Vocal_2 MDX-Net model has "unclear licensing status for commercial applications" (open issue requesting MIT). — [AEmotionStudio/roformer-models](https://huggingface.co/AEmotionStudio/roformer-models); [KimberleyJensen issue #3](https://github.com/KimberleyJensen/kmdx-net_music-source-separation/issues/3). The 2026 RoFormer guide states "each model weight's distribution terms are individual". — [tomodahinata](https://tomodahinata.com/en/blog/bs-roformer-mel-band-roformer-vocal-separation-guide)
- Spleeter dropped its dedicated GPU package in 2.1.0 and no longer recommends conda. — [deezer/spleeter](https://github.com/deezer/spleeter)
- Alternative non-Python runtimes for Demucs exist (C++/ggml `stems.cpp`, Rust/wgpu `demucs-wgpu`, TensorRT export) if deployment without PyTorch is desired. — [tinycrops/stems.cpp](https://github.com/tinycrops/stems.cpp); [eclipse005/demucs-wgpu](https://github.com/eclipse005/demucs-wgpu); [Demucs_v4_TRT](https://huggingface.co/MansfieldPlumbing/Demucs_v4_TRT)

### Inferences
- A consumer RTX card with >=8 GB VRAM comfortably runs Demucs; for RoFormer models with audio-separator, reduce `segment_size`/batch or use fp16 if OOM occurs. CPU-only is viable for Demucs (minutes per song) but RoFormer on CPU will be considerably slower (no measured figure found).
- For a redistributable tool, use MIT code + MIT weights (Demucs htdemucs/htdemucs_ft/htdemucs_6s; Kimberley Jensen Mel-Band RoFormer vocal model; MVSEP's MUSDB18-trained BS/Mel-RoFormer and SCNet XL releases, license to be verified per release). Treat BS-RoFormer-SW 6-stem and other re-hosted UVR-community checkpoints as "use at your own risk, non-redistributable" until a license appears.

### Gaps
- No measured VRAM or per-song runtime numbers for BS-/Mel-Band RoFormer inference on consumer GPUs or CPU were found in primary sources.
- Exact current audio-separator version and its pinned torch/onnxruntime versions were not visible in the fetched README.
- License text for the MVSEP January-2025 MUSDB18 weight releases was not fetched.

## Key Question 7: Post-separation — does chord recognition / transcription on stems beat the full mix?

### Takeaway
Evidence is mixed and thin: one informal study (Demucs other+bass into a CNN-BiLSTM chord model) found separated input performed worse than the mix; a 2025 APSIPA paper (HTDemucs preprocessing with pitched stems boosted, then a BTC Transformer) reports improved accuracy with >2,000 misrecognized frames corrected; guitar-string separation improves tablature transcription but artifacts limit gains. The most defensible design is "separate, then re-mix with emphasis" (boost guitar/keys/bass, attenuate vocals/drums) rather than feeding a single stem.

### Cited Findings
- Daniel Ko (UW-Madison, undated project page): Demucs "other" and bass stems combined, CNN (9 conv) + BiLSTM chord model (Jiang et al.), Humphrey & Bello 1,217-song dataset: "On average across all metrics, the Demucs model performed worse than the model that was trained using the original dataset"; author attributes it to separation artifacts. No numeric values in text. — [Automatic Chord Recognition by Music Source Separation](https://ko28.github.io/chord-transcription/)
- Mitoma & Furuya (Oita University), "Accuracy Improvement of Automatic Chord Recognition with Source Separation Preprocessing", APSIPA ASC 2025: uses HTDemucs 4-stem separation as preprocessing for the BTC (bi-directional Transformer) chord recognizer; "by amplifying the volume of pitched instruments, such as a piano and guitar, the proposed method successfully corrected more than 2,000 misrecognized chord frames and improved the overall recognition accuracy compared with the conventional method." — [APSIPA 2025 paper PDF](http://www.apsipa.org/proceedings/2025/papers/APSIPA2025_P307.pdf)
- Jointist (joint transcription + separation): chord recognition "improved by 1.4 percentage points when utilizing transcription results obtained from Jointist." — [arXiv 2302.00286](https://arxiv.org/pdf/2302.00286)
- Chang, Chen, Chen, Su (2025-09-23): LLM chain-of-thought over MIR tool outputs (including source separation, key, beat) gives "overall accuracy gains of 1-2.77% on the MIREX metric" (GPT-4o); separation's isolated contribution not reported. — [arXiv 2509.18700](https://arxiv.org/abs/2509.18700)
- Guitar string separation (multi-channel Wave-U-Net; GS-Aux and ADGP datasets from GuitarSet/DadaGP) "improves transcription performance in comparison to the original soundtrack, though performance is still sub-optimal due to artifacts" (IEEE TASLP, Jan 2025). — [Separate and Transcribe](https://ieeexplore.ieee.org/document/11179987/)
- Derby et al. (Dec 2024), "Source Separation & Automatic Transcription for Music": end-to-end stems -> MIDI -> MuseScore pipeline; abstract gives no quantitative stem-vs-mix comparison. — [arXiv 2412.06703](https://arxiv.org/abs/2412.06703)
- Cocktail Fork (separation then transcription for soundtracks) and "Transcription Is All You Need" (score-supervised separation) are related joint-task works. — [arXiv 2212.07327](https://arxiv.org/pdf/2212.07327); [ResearchGate](https://www.researchgate.net/publication/352170839_Transcription_Is_All_You_Need_Learning_To_Separate_Musical_Mixtures_With_Score_As_Supervision)
- MVSEP's "Ensemble All-In" (vocals, bass, drums, piano, guitar, lead/back vocals, other) averages SDR 13.67 (v. 2025.06.30) on MVSEP's set — representative of what hosted ensembles achieve vs single models. — [MVSEP algorithms](https://mvsep.com/en/algorithms)

### Inferences
- Chord recognizers trained on full mixes expect mix-like spectra; feeding a single artifact-laden stem shifts the input distribution (Ko's negative result). The APSIPA approach (re-mix with pitched instruments boosted) keeps the input mix-like while raising harmonic SNR, which is why it helps. For this pipeline: run chord recognition on (a) the original mix and (b) a re-mix of guitar+piano+other+bass with vocals/drums attenuated, and reconcile; run note-level transcription (for melody/tab) on the bass stem and the guitar/lead stem.
- Newer, cleaner stems (BS-RoFormer-SW vs the 2020-era Demucs used by Ko) plausibly change the result, but no study with RoFormer-class stems and chord recognition was found.

### Gaps
- Exact accuracy numbers from the APSIPA 2025 paper could not be extracted (PDF not text-parsable in this environment); only the qualitative claim and ">2,000 frames corrected" are sourced.
- No peer-reviewed study was found comparing chord recognition on RoFormer/Demucs-v4 stems vs. mixes on standard datasets (Isophonics/Billboard/McGill) with reported WCSR.
- No paper or blog was found on guitar-tab transcription from commercial-mix guitar stems (as opposed to solo-guitar recordings); the guitar-string-separation work assumes a solo guitar input.
