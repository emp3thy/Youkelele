# Key estimation from audio and stems; resolving a YouTube video's true title and artist (as of 2026-10)

Scope note: findings below are from primary docs, papers and repos fetched 2026-10-08. Where only a secondary aggregator (paperswithcode, a git mirror) was reachable, that is said. Reddit was not used.

## Key question 1: What do the classical profile methods, Essentia KeyExtractor, madmom's CNN and recent deep models score, how do they confuse relative keys, what confidence do they expose, and what installs on Windows?

### Takeaway
On the standard 604-track GiantSteps (EDM) test set, everything from Essentia's EDM profiles to 2025 self-supervised models sits in a 65–75 % MIREX weighted-score band; on pop/rock (Billboard, Isophonics) supervised CNNs reach ~82–85 % weighted (76–80 % exact). Errors are dominated by fifth, relative and parallel confusions at a combined 15–25 %, so a D-major-for-G-major result (a fifth error) is the single most common systematic mistake these systems make. Only madmom (with build pain) and the research repos are pip-reachable on Windows; Essentia's Python bindings are not.

### Cited Findings

**Scoring convention (needed to read every number below)**
- mir_eval `weighted_score`: same key and mode 1.0; estimate a perfect fifth above reference 0.5; relative major/minor (same key signature) 0.3; parallel major/minor (same tonic) 0.2; other 0.0; with `allow_descending_fifths=True` a fifth below also scores 0.5 — [mir_eval key docs](https://mir-eval.readthedocs.io/latest/api/key.html)
- Korzeniowski & Widmer compute the same thing as correct + 0.5·fifth + 0.3·relative + 0.2·parallel — [Korzeniowski & Widmer 2018 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1808.05340)
- The 2017 paper's error taxonomy: a relative error is "predicted mode minor with the tonic 3 semitones below the target, or predicted mode major with the tonic 3 semitones above" — [Korzeniowski & Widmer 2017 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1706.02921)

**Datasets**
- GiantSteps Key: 604 Beatport previews, most 120 s, EDM; cited as Knees, Faraldo, Herrera, Vogl, Böck, Hörschläger, Le Goff, ISMIR 2015; the dataset page says it carries a benchmark table of published algorithms and commercial products, but neither the JKU page nor the GitHub README rendered it to my fetches, and no licence is stated — [GiantSteps key dataset repo](https://github.com/GiantSteps/giantsteps-key-dataset); [JKU dataset page](https://www.cp.jku.at/datasets/giantsteps/)
- GiantSteps-MTG Key (training set): 1,486 previews, of which 1,077 single-key high-confidence excerpts are used for training in the Korzeniowski papers — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- McGill Billboard: 625 of 742 songs have key labels; Isophonics key subset: 180 Beatles + 19 Queen + 18 Zweieck songs split into single-key segments; KeyFinder set: 998 songs with audio; "Rock" set: 200 songs — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- Schreiber & Müller use GTZAN Key (836 30 s excerpts, 10 genres) and LMD Key (6,981 30 s excerpts, mostly rock/pop, which "contains no C major tracks") — [Schreiber & Müller 2019 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1903.10839)

**Krumhansl-Schmuckler / Temperley / profile methods**
- Essentia's `Key` algorithm offers profiles `diatonic`, `krumhansl` ("based on listening experiments; works generally well for pop"), `temperley` ("from classical corpus analysis; best on that repertoire, especially minor keys"), `shaath` (Krumhansl tuned for popular/electronic), `noland` (Bach WTC), `edma` (auto-extracted from EDM; "often outperforms Shaath"), `edmm` (edma hand-adjusted; "reports major keys as minor, but performs better otherwise"), `braw` ("median profile per mode from a BeatPort subset, plus an extra minor profile for ambiguous tracks"), `bgate` (default; "like braw, but zeroes the four least relevant elements of each profile"); other parameters `usePolyphony`, `useThreeChords` (tonic/dominant/subdominant triads only), `numHarmonics` (default 4), `slope` (0.6), `pcpSize` (36), `averageDetuningCorrection`; outputs are `key`, `scale` and `strength` ("the strength of the estimated key"); `useMajMin` "allows classifying songs as MajMin" and is only available for edma, bgate, braw; references are Gómez 2006, Temperley 1999, Faraldo et al. 2016 and Faraldo, Jordà, Herrera 2017 — [Essentia Key reference](https://essentia.upf.edu/reference/streaming_Key.html)
- On GiantSteps, the EDM profile family run through Essentia scores: EDMA 65.6 weighted (57.8 correct, 7.3 fifth, 6.6 relative, 10.8 parallel, 17.6 other); EDMM 70.1 (63.7 / 8.6 / 2.7 / 6.5 / 18.5); EDMT (Temperley-style) 44.6 (33.6 / 8.8 / 15.4 / 9.9 / 32.3); the QM Vamp key detector 50.4 (39.6 / 11.9 / 13.2 / 4.3 / 31.0) — [Korzeniowski & Widmer 2017](https://ar5iv.labs.arxiv.org/html/1706.02921)
- On the Billboard test split the same profiles flip: EDMA 78.7 weighted (70.8 correct, 11.8 fifth, 2.8 relative, 5.6 parallel, 9.0 other); EDMM collapses to 28.9 (14.6 correct, 42.4 parallel) because of its minor bias; EDMT 75.4 (66.7 / 12.5 / 6.3 / 2.8 / 11.8); QM 60.9 — [Korzeniowski & Widmer 2017](https://ar5iv.labs.arxiv.org/html/1706.02921)
- `bgate` (Faraldo's multi-profile method, via the open-source edmkey implementation) on the KeyFinder pop set: 72.4 weighted (65.0 correct, 8.6 fifth, 6.5 relative, 5.4 parallel, 14.4 other) — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- A plain Krumhansl template matcher scores 53.4 % MIREX / 60.1 % key-signature accuracy / 64.9 % mode accuracy on FMAKv2 (5,489 songs) — [S-KEY, Kong et al. 2025 (arXiv 2501.12907v2)](https://arxiv.org/html/2501.12907v2)
- Temperley's 1999 reconsideration of Krumhansl-Schmuckler makes four changes (simpler matching formula, different profiles, segment-wise binary pitch-class presence, a penalty for changing key between segments) and was tested on Bach WTC fugue subjects and Kostka-Payne textbook excerpts — [Temperley 1999, "What's Key for Key?" (PDF)](https://music.informatics.indiana.edu/courses/I546/pdf/temperley.pdf)
- Albrecht & Shanahan (Music Perception 31(1), 2013) trained a Euclidean-distance profile on 490 classical pieces, tested on 492, found most existing models were "more accurate on major-mode works than on minor-mode works", and that combining their model with Aarden-Essen gave "significantly more accurate key assessments than all other extant models" — [University of Iowa record](https://iro.uiowa.edu/esploro/outputs/journalArticle/The-use-of-large-corpora-to/9984446432402771)
- A 2022 Applied Sciences study comparing Krumhansl-Kessler, Temperley and Albrecht-Shanahan profiles with a "signature of fifths" method on Bach preludes, Chopin preludes and Beatles songs reports the signature method beating the correlational profiles by an average of 9.27 percentage points when aggregate pitch-class durations are used — [DOAJ record](https://doaj.org/article/1b116c5c9ce14567b8416f3ea4df7910)

**madmom CNN**
- `madmom.features.key.CNNKeyRecognitionProcessor` "estimates the global key of a musical piece with a convolutional neural network" per Korzeniowski & Widmer ISMIR 2018; with `nn_files=None` it "uses an ensemble of networks"; it returns a probability per key class (a 1×24 array in the docs example); `key_prediction_to_label` maps that vector to a name — [madmom key module docs](https://madmom.readthedocs.io/en/v0.16.1/modules/features/key.html)
- The paper behind it (AllConv): GiantSteps 74.6 weighted (67.9 correct, 7.0 fifth, 8.1 relative, 4.1 parallel, 12.9 other); Billboard 85.1 (79.9 / 5.6 / 4.2 / 6.2 / 4.2); Isophonics (Beatles etc.) 82.5 (76.3 / 7.6 / 5.4 / 3.7 / 7.1); KeyFinder 76.1; Robbie Williams 81.2; Rock 74.3 (69.3 correct, 16.5 other); Classical 96.6 — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- Same paper's length finding: on the Rock set, correctly classified excerpts had median length 131 s vs 51 s for misclassified ones; authors conclude "short excerpts are more often misclassified" — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- 2017 predecessor (CK1): GiantSteps 74.3 weighted; trained on Billboard instead (CK2) it drops to 57.3 on GiantSteps with 12.6 % relative and 16.6 % parallel errors; "the most common error occurring in these cross-genre setups is predicting the wrong mode" — [Korzeniowski & Widmer 2017](https://ar5iv.labs.arxiv.org/html/1706.02921)
- Independent 2025 re-measurement of madmom's shipped model: 73.1 % MIREX on FMAKv2, 67.9 % on GTZAN, 71.0 % on GiantSteps (the authors note this is below the paper's 74.6), 87.7 % on SWD (Schubert Winterreise); mode accuracy 79.3 % on FMAKv2 — [S-KEY 2025](https://arxiv.org/html/2501.12907v2)
- Install status: the latest release on piwheels is 0.16.1 dated 2018-11-14 — [piwheels madmom](https://www.piwheels.org/project/madmom); a madmom issue reports that "Cython is in the dependencies, but not installed before executing setup.py, causing the package install to fail", still present as of April 2024, with the workaround of installing cython and numpy first — [madmom issue #463 (git mirror of CPJKU/madmom)](https://git.tdem.in/CPJKU/madmom/issues/463); a Windows build failure report shows a source build requiring Visual Studio Build Tools — [madmom issue #478 (mirror)](https://git.tdem.in/CPJKU/madmom/issues/478)

**Essentia on Windows**
- Essentia's install page: pip wheels are documented for Linux only ("pip install essentia"); for Windows "Python bindings are not supported yet", the C++ library can be cross-compiled with MinGW, and Essentia "can run inside Windows Subsystem for Linux (WSL)" — [Essentia installing](https://essentia.upf.edu/installing.html)

**Recent deep / self-supervised models (2019–2026)**
- Schreiber & Müller 2019 (SMC): directional-filter CNNs trained on MTG Key (1,158 EDM excerpts) reach only 58.5 ± 3.9 % plain accuracy on GiantSteps, 49.9 % on GTZAN Key, 71.3 % on LMD Key, versus 67.9 % plain accuracy for Korzeniowski 2018; the paper deliberately reports accuracy only, not the MIREX score; code at github.com/hendriks73/directional_cnns — [Schreiber & Müller 2019 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1903.10839)
- Baumann, ISMIR 2021, "Deeper Convolutional Neural Networks and Broad Augmentation Policies Improve Performance in Musical Key Estimation" (InceptionKeyNet): "can significantly outperform state-of-the-art single-task models when trained on the same datasets"; paperswithcode lists 75.68 % accuracy on GiantSteps "using extra training data" — [paperswithcode entry](https://astro.paperswithcode.com/paper/deeper-convolutional-neural-networks-and); [ISMIR 2021 PDF](https://archives.ismir.net/ismir2021/paper/000004.pdf); the reference implementation is MIT-licensed and ships no pretrained weights; audio must be sourced separately except GiantSteps — [inceptionkeynet repo](https://github.com/stefan-baumann/inceptionkeynet)
- STONE (2024): self-supervised tonality estimator on a ChromaNet; notes GSMK/GSK are the standard supervised train/test sets — [STONE (arXiv 2407.07408)](https://arxiv.org/html/2407.07408v1)
- S-KEY (Deezer / Nantes, 2025): self-supervised 24-key estimator with no human labels; MIREX scores S-KEY(60k)/S-KEY(1M)/madmom: FMAKv2 72.1/73.2/73.1; GTZAN 70.9/74.4/67.9; GiantSteps 71.7/72.1/71.0; SWD 89.0/90.4/87.7; mode accuracy on FMAKv2 79.0 % vs madmom 79.3 %; on GTZAN both methods exceed 90 % on country and fall below 50 % on blues, and the authors argue the 24-key taxonomy "fits blues, jazz and hip-hop poorly"; training and inference code at github.com/deezer/s-key (weights not explicitly promised) — [S-KEY 2025](https://arxiv.org/html/2501.12907v2)
- KeyMyna (Yonay, Hammond, Yang, arXiv April 2026): masked contrastive pre-training on Mel spectrograms; "shallow, wide MLPs trained on the frozen features reach state-of-the-art results" on key detection; code and models at github.com/echo-cipher/keymyna; the abstract page gives no numbers — [arXiv 2604.10021](https://arxiv.org/abs/2604.10021)
- Parameter-efficient transfer learning for music foundation models (2024) evaluates key on GiantSteps with mir_eval weighted accuracy, training on GiantSteps-MTG — [arXiv 2411.19371](https://arxiv.org/pdf/2411.19371)

**Confidence / hedging measures exposed**
- Essentia: `strength` (correlation of the PCP with the winning profile) and the `MajMin` third class via `useMajMin` for the edma/bgate/braw profiles; braw adds "an extra minor profile for ambiguous tracks" — [Essentia Key reference](https://essentia.upf.edu/reference/streaming_Key.html)
- madmom: the full 24-way probability vector (ensemble-averaged), from which top-2 margin can be read — [madmom key docs](https://madmom.readthedocs.io/en/v0.16.1/modules/features/key.html)
- Bernardes et al. 2017 (BD1 in Korzeniowski's tables) uses an "adaptive mode bias" to steer major/minor; it scores 75.1 on Isophonics with 13.6 % fifth errors — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- None of the fetched papers report a calibrated confidence threshold for abstaining; they report only hard decisions scored by category.

### Inferences
- The user's Badge result (D major printed; references say G major / E minor) is a textbook "fifth" error against G major. Fifth errors run 5.6–13.6 % on pop/rock datasets even for the best CNN, and the dominant (D) shares six of seven pitch classes with the tonic (G), so a chroma-profile vote is inherently weak here; the discriminating evidence is where phrases cadence, not pitch-class weight.
- G major vs E minor (relative) is scored 0.3 by MIREX precisely because the datasets themselves treat it as semi-correct; published tabs disagreeing between G major and E minor for the same song is evidence that a hedge of the form "G major (or E minor)" is the right output class for pop songs with modal/relative ambiguity, and Essentia's `MajMin` class is the closest precedent in a shipping library.
- Given the 2026 literature, the practical ceiling for a generic (non-genre-tuned) estimator is roughly 70–75 % exact and 80–85 % weighted on pop/rock. A three-rule vote of chroma-profile scores will not beat madmom's ensemble; the cheapest accuracy gain for a Windows pip project is to add madmom's 24-way probability vector as a fourth, more heavily weighted voter, with the profile methods kept as tie-breakers.
- A hedging rule consistent with the error tables: hedge when the top-2 candidates are fifth-, relative- or parallel-related AND the top-2 margin is small (Essentia `strength` ratio or madmom probability gap); print a hard answer when the runner-up is an unrelated key (the "other" category), because in that case the leader is usually right.
- Excerpt length matters: estimate on the whole song (or at least >2 min of it) rather than a 30 s window; Korzeniowski's Rock-set medians (131 s correct vs 51 s wrong) show short windows roughly double the error.

## Key question 2: Should key be estimated on the mix, on harmonic stems, or on the chord sequence, and what does the literature say about combining them?

### Takeaway
I found no peer-reviewed study that measures key accuracy on Demucs-style stems versus the mix; the literature's combination story is instead (a) joint chord+key HMMs (Lee & Slaney 2007) and (b) key-conditioned chord labelling pipelines, with harmonic/percussive separation treated as a generic pre-processing step whose benefit for key is asserted, not measured.

### Cited Findings
- Lee & Slaney (ISMIR 2007), "A Unified System for Chord Transcription and Key Extraction Using Hidden Markov Models": each of the 24 major/minor keys is a separate HMM "similar to an isolated-word recognizer"; parameters are estimated from labelled training data built by harmonically analysing symbolic music and synthesising audio; experiments "indicate that the model estimates the key and also gives higher chord recognition accuracy than a universal, key-independent model" — [ISMIR 2007 paper](https://archives.ismir.net/ismir2007/paper/000245.pdf); journal version in IEEE TASLP 16(2):291–301 is listed on the author's page — [Kyogu Lee, CCRMA](https://ccrma.stanford.edu/~kglee/)
- A 2026 piano-repertoire analysis pipeline runs Essentia KeyExtractor (default `bgate`) first and then "maps detected chords to scale degrees relative to that tonic", i.e. key decided before chord labelling, not jointly; it describes bgate as "reported to outperform the classical Krumhansl-Kessler profile on a broad range of tonal repertoire" — [arXiv 2605.06685](https://arxiv.org/pdf/2605.06685)
- Music-theory framing of why chord labels alone cannot separate relative keys: the defining scale degrees for major are the fourth and seventh (contained in the dominant and leading-tone chords); minor is defined by the second, fourth and sixth degrees; "overlapping, common chords in closely related keys can create ambiguity" — [RWU Music Theory (pressbooks)](https://rwu.pressbooks.pub/musictheory/?p=269)
- Harmonic/percussive separation (HPSS) as preprocessing: Park & Lee (ISMIR 2015) state that for rhythm tasks such as tempo estimation "harmonic signals act as interference" and that conventional HPSS struggles with time-varying harmonic sounds such as vocals, vibrato and glissando — [Park & Lee, ISMIR 2015](https://www.ismir2015.uma.es/articles/219_Paper.pdf)
- A 2026 stem-based AI-music-detection paper notes that HTDemucs's authors flag piano separation as a weak point and that detector confidence "hover[s] around 0.5" during low-energy or silent passages of a stem — [arXiv 2609.26956](https://arxiv.org/pdf/2609.26956)
- Essentia's `Key` has `usePolyphony` (triad and pitch-harmonic contributions) and `useThreeChords` (profile built from only tonic, dominant, subdominant triads) — a chord-aware profile inside a chroma method — [Essentia Key reference](https://essentia.upf.edu/reference/streaming_Key.html)
- Korzeniowski & Widmer's CNN takes the full mix (log-frequency spectrogram) and still reaches the best published pop/rock numbers (85.1 weighted on Billboard) without any separation — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)

### Inferences
- Stems are not a documented accuracy win for key. The two reasons to use them are practical: (1) the bass stem carries the roots of chords and the cadence bass line, which is the information a tonic-vs-dominant decision needs; (2) the drum stem adds broadband energy to chroma that profile methods must average out. Neither is quantified in the literature found; treat a stems-based voter as an engineering experiment, validated on the project's own blind songs.
- A chord-sequence voter is better placed to resolve the fifth/relative ambiguities than another chroma profile: it can apply cadence rules (does the song end on G or on D; is there a D→G or B7→Em dominant-tonic motion; how often does F# appear as a chord root, which would argue for D major). Lee & Slaney's result (key-specific models improve chord accuracy) is the formal version of this coupling.
- Combination guidance that the evidence supports: weight voters by their measured per-category error, not equally. A chroma-profile voter is strong on "other" rejection but weak on fifth/relative; a chord/cadence voter is strong on fifth/relative but needs a correct chord transcription; the CNN is strongest overall on pop. A sensible merge is: take the CNN's top-2; if the chord-cadence rule agrees with the leader, print it; if it prefers the runner-up and the runner-up is fifth/relative/parallel-related, hedge.

### Gaps
- No study measuring key accuracy on separated stems (Demucs/HTDemucs/Spleeter) versus mixtures was found despite targeted searches; this is an open question and the project's own A/B on labelled songs is the only route.
- Lee & Slaney's numeric key-accuracy results were not retrieved (PDF fetched as binary).
- No published "chord labels → key with tonic-cadence rule" algorithm with an evaluation was found; the chord-based reasoning above comes from theory texts and inference.

## Key question 3: How reliable are yt-dlp's music fields, AcoustID/Chromaprint + MusicBrainz, shazamio, and title-parsing, and what are the limits, licences, keys and Windows notes?

### Takeaway
yt-dlp fills `track`/`artists`/`album`/`release_year` only from YouTube's own "Music in this video" rows or the Auto-generated-by-YouTube description, and deliberately skips those rows when more than one song is credited; `uploader` is never the artist. AcoustID (free key, 3 req/s, non-commercial) with pyacoustid 1.3.1 and an `fpcalc.exe` on PATH is the most principled fallback; shazamio (reverse-engineered, 12 s signature) is the most robust on covers/live/fan uploads but carries no terms; title parsing (`youtube-title-parse`, last pushed 2022) is a last resort.

### Cited Findings

**yt-dlp fields**
- Output-template fields "available for the media that is a track or a part of a music album": `track` (title of the track), `track_number`, `track_id`, `artists` (list) / `artist` (comma-separated string), `genres`/`genre`, `composers`/`composer`, `album`, `album_type`, `album_artists`/`album_artist`, `disc_number`; general fields include `title`, `description`, `uploader` ("Full name of the video uploader"), `channel`, `creators`/`creator`, `release_date` (YYYYMMDD), `release_year` ("Year (YYYY) when the video or album was released") — [yt-dlp README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)
- Where the YouTube extractor gets them (current master): path 1, if the description ends with "Auto-generated by YouTube." a regex reads `(?P<track>[^\n·]+) · (?P<artist>[^\n]+)`, `℗\s*(?P<release_year>\d{4})`, `Released on\s*:\s*(?P<release_date>\d{4}-\d{2}-\d{2})` and `Artist\s*:\s*(?P<clean_artist>[^\n]+)`; artists are split on " · "; `release_year` falls back to `release_date[:4]`; path 2, `videoSecondaryInfoRenderer → metadataRowContainerRenderer → rows → metadataRowRenderer` with titles `License`, `Album`, `Artist`, `Song`; the loop sets `multiple_songs = True` and breaks on any row with `hasDividerLine`, after which `Album`, `Artist` and `Song` are skipped entirely (only `License` is read); row values overwrite the description values; finally `artists` is copied to `creators` and `track` to `alt_title`; the test suite still carries `# TODO: fix metadata extraction` on an auto-generated-description case and `'channel': 'Stephen', # TODO: should be 'Stephen - Topic'` — [yt_dlp/extractor/youtube/_video.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_video.py)
- History: youtube-dl commit for #20301 "[youtube] extract album from Music in this video section" moved album extraction to that panel with description fallback — [youtube-dl commit 92bc97d (gitdab mirror)](https://gitdab.com/w/youtube-dl/commit/92bc97d398cb66e4968070f9d73f02a367193c2b); yt-dlp #8917 (2024) migrated `artists`, `genres`, `album_artists` to lists with comma-joined string twins — [yt-dlp commit (mirror)](https://git.myzel394.app/Myzel394/yt-dlp/commit/1732eccc0a40256e076bf0435a29f0f1d8419280.patch)
- `--parse-metadata FROM:TO` extracts from a field or template string into target fields via a regex with named groups; `--replace-in-metadata FIELDS REGEX REPLACE`; worked example `--parse-metadata "title:%(artist)s - %(title)s"` "interprets the title as Artist - Title"; the default embedding map takes file `artist` from `artist`, `artists`, `creator`, `creators`, `uploader` or `uploader_id` in that order and file `title` from `track` or `title` — [yt-dlp README, Modifying metadata](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)
- ytmusicapi `get_song(videoId)` returns `videoDetails` with `author` (example "Oasis - Topic"), `title` ("Wonderwall") and `musicVideoType` ("MUSIC_VIDEO_TYPE_ATV" for an Art Track); key names changed between 0.17 (`artist`) and 0.19 (`artists`) in list results — [ytmusicapi reference 0.19.0](https://ytmusicapi.readthedocs.io/en/0.19.0/reference.html)

**AcoustID / Chromaprint / MusicBrainz**
- AcoustID web service: lookup requires `client` (application API key obtained by registering; the example key expires in days), `duration` (whole-file seconds) and `fingerprint`; `meta` accepts `recordings`, `recordingids`, `releases`, `releaseids`, `releasegroups`, `releasegroupids`, `tracks`, `compress`, `usermeta`, `sources`, `isrcs`, combinable with `+`; each result carries a `score` (1.0 in the examples; scale not defined further); limit "no more than 3 requests per second"; "free for non-commercial use only", commercial via acoustid.biz; heavy users should contact the operators — [AcoustID web service docs](https://acoustid.org/webservice)
- pyacoustid 1.3.1 (released 2026-04-09; previous 1.3.0 2023-09-12), Python ≥3.10, MIT; needs the Chromaprint shared library or the `fpcalc` CLI on PATH or pointed to by `FPCALC`; `acoustid.match(apikey, path)` yields `(score, recording_id, title, artist)` tuples with score in [0,1]; the module "performs thread-safe rate limiting of 3 queries per second"; decoding is capped at 120 s of audio; `NoBackendError`/`FingerprintGenerationError`/`WebServiceError` are the failure classes; Windows fixes landed in 1.0.0 (Unicode filenames with fpcalc), 1.2.0 and 1.3.0 (DLL search paths) — [pyacoustid on PyPI](https://pypi.org/project/pyacoustid/)
- beets' chroma plugin: "the simplest way to get up and running on Windows is to download the Chromaprint binary package and place fpcalc.exe on your shell search path" — [beets chroma plugin docs](https://docs.beets.io/en/stable/plugins/chroma.html)
- MusicBrainz API rate limiting: checks User-Agent, then source IP, then global; "about 1 request/second" per IP, ~300/s global; a User-Agent of the form `Application/<version> ( contact-url-or-email )` is required, and generic Python-urllib/Java/"-" agents are treated as anonymous and throttled; denied requests get HTTP 503 — [MusicBrainz API rate limiting](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)
- MusicBrainz data licence: core data CC0 ("effectively placing the data into the Public Domain"); supplementary data and the Live Data Feed CC BY-NC-SA 3.0 — [MusicBrainz data licence](https://musicbrainz.org/doc/About/Data_License)

**shazamio**
- Built from a "reverse engineered Shazam API" (not official); `pip install shazamio`, Python 3.10+, asyncio/aiohttp, MIT; `recognize()` accepts a path, `pathlib.Path` or raw bytes and returns a dict; "the signature uses the first 12 seconds of audio. Shazam finds nothing from 15 seconds up"; `segment_duration_seconds` exists but is "not recommended" and warns; `max_skew=1e-3` rejects skewed matches but is off by default because it "also rejects sped-up, slowed, or pitch-shifted audio"; Shazam has retired its text-search endpoints so text search now goes through Apple's iTunes index; no rate-limit, proxy, ffmpeg or Windows notes in the README — [ShazamIO repo](https://github.com/shazamio/ShazamIO)
- PyPI: version 0.8.1 released 2025-06-11; Requires-Python <4.0, ≥3.10 (the long description still says 3.8+); MIT; no dependency list shown; result fields such as `track.subtitle` or ISRC are not documented on the page — [shazamio on PyPI](https://pypi.org/project/shazamio/)
- No official Shazam rate limit applies to shazamio; a third-party RapidAPI Shazam wrapper caps at 60–240 requests/minute by tier and returns HTTP 429 above that, and notes ShazamKit "does not publish explicit rate limits" — [apis.io Shazam rate limits](https://apis.io/rate-limits/shazam/shazam-rate-limits/)

**Title parsing**
- `youtube-title-parse` (PyPI): "a Python3 rewrite of the equivalent npm library, get-artist-title, but adds some extra functionality"; `get_artist_title(title)` returns `[artist, title]` or `[None, None]`; MIT — [youtube-title-parse on PyPI](https://pypi.org/project/youtube-title-parse/); repo last pushed April 2022 — [ecosyste.ms record](https://awesome.ecosyste.ms/projects/github.com%2Flttkgp%2Fyoutube_title_parse)
- npm `get-artist-title`: regex splitting on separators like " - ", strips suffixes such as "(Music Video)", returns `[artist, title]` or `null`; has a `defaultArtist` option because "a YouTube video title may not always contain the artist name, but the name of the channel that uploaded it might be relevant" — [get-artist-title on npm](https://npmjs.com/package/get-artist-title)

### Inferences
- The project's "The Beatles - Day Tripper by Natan Santos" failure is exactly the `uploader`-as-artist fallback in yt-dlp's own embedding map (artist ← artist/artists/creator/creators/uploader/uploader_id). Reading `artists`/`track` first and treating `uploader` as the artist only when the channel is a Topic/VEVO-style artist channel (e.g. `author` ending in " - Topic" in ytmusicapi, or `channel` equal to the parsed artist) removes the worst case without any network call.
- Because yt-dlp blanks `Song`/`Artist`/`Album` when YouTube credits more than one song (`multiple_songs`), compilations, mashups and long fan videos will return nothing, not a wrong answer; the pipeline should distinguish "absent" from "disagrees".
- Reliability ordering for a single-song pop upload, from the evidence: (1) yt-dlp `track`+`artists` when present (they come from label-supplied YouTube Music credits, not the uploader); (2) AcoustID match with high `score` carrying a MusicBrainz recording (CC0 core data, documented 3 req/s, API key free); (3) shazamio (best on covers/live/re-uploads because it is a recognition service, but undocumented terms and a 12 s window); (4) `youtube-title-parse` of the title with the channel name as `defaultArtist`; (5) raw `uploader`. AcoustID is fingerprint-of-the-recording, so a cover or live version will not match the studio recording and the absence of a match is itself a signal that the video is not the canonical recording.
- Licence/terms fit for a hobby project: AcoustID free for non-commercial; MusicBrainz CC0 core + mandatory User-Agent; shazamio MIT code but Shazam's service terms are unaddressed; yt-dlp Unlicense (not fetched here) reading public pages; all four install with pip on Windows, the only binary being `fpcalc.exe` from the Chromaprint release (or `libchromaprint` found by pyacoustid 1.3.x's extended DLL search).

### Gaps
- No measured precision/recall of yt-dlp's `track`/`artist` fields across a corpus of YouTube videos was found; reliability statements rest on reading the extractor code and its TODO comments.
- AcoustID's `score` semantics (what value separates a confident match) are not defined in the web-service doc; no published threshold found.
- shazamio's actual throttling behaviour, the structure of `recognize()`'s raw dict (`track.title`, `track.subtitle`, ISRC) and its handling of Windows paths were not confirmed from the README or PyPI; the Chromaprint `fpcalc` Windows binary download page was not fetched.
- YouTube Data API v3 (official, API-key, quota-based) was not researched here.
- No independent evaluation of `youtube-title-parse` accuracy exists in the sources found.

## Key question 4: What should a small project do when sources disagree (confidence ordering, printing a hedge)?

### Takeaway
No published recipe for a small key+metadata pipeline was found; the defensible design assembles the pieces above: an ordered-evidence policy for metadata (credited fields > fingerprint > recognition > title parse > uploader) and a category-aware hedge for key (hedge only when the runner-up is fifth/relative/parallel-related and the margin is small), with both printed as explicit provenance on the sheet.

### Cited Findings
- Essentia ships a three-way answer (`major`, `minor`, `MajMin`) for ambiguous tracks via `useMajMin`, and `braw` includes an extra minor profile for ambiguous tracks — a shipping precedent for a hedged key class — [Essentia Key reference](https://essentia.upf.edu/reference/streaming_Key.html)
- MIREX/mir_eval score fifth, relative and parallel errors at 0.5/0.3/0.2, so the community already treats these as partially correct — [mir_eval key docs](https://mir-eval.readthedocs.io/latest/api/key.html)
- madmom exposes a 24-way probability vector, so a top-2 margin is available for free — [madmom key docs](https://madmom.readthedocs.io/en/v0.16.1/modules/features/key.html)
- Korzeniowski & Widmer 2018 show "other" errors fall to 4–7 % on pop/rock while fifth+relative+parallel together stay at 15–20 % — [Korzeniowski & Widmer 2018](https://ar5iv.labs.arxiv.org/html/1808.05340)
- S-KEY shows mode accuracy (~79 %) is the weakest component for both supervised and self-supervised models, and that genre swings results from >90 % (country) to <50 % (blues) — [S-KEY 2025](https://arxiv.org/html/2501.12907v2)
- pyacoustid returns a ranked iterable of `(score, recording_id, title, artist)`, i.e. multiple candidates with confidence — [pyacoustid on PyPI](https://pypi.org/project/pyacoustid/)
- yt-dlp's embed map falls through artist → artists → creator → creators → uploader → uploader_id, encoding a built-in confidence ordering in which uploader is last — [yt-dlp README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)
- get-artist-title's `defaultArtist` option exists because the channel name is only "might be relevant" evidence of the artist — [get-artist-title on npm](https://npmjs.com/package/get-artist-title)

### Inferences
- Metadata policy that the sources support: accept a source only if it agrees with at least one independent source or is the highest-ranked and the lower ones are absent; when two ranked sources disagree on artist, print the higher-ranked one and the other in parentheses ("Cream — Badge (uploader: SomeChannel)"); never print `uploader` as the artist unless the channel name matches the parsed artist or ends in " - Topic".
- Key policy: compute a 24-way score from the strongest voter (madmom if it installs; otherwise the profile score), take top-2; classify the pair with mir_eval's categories; if the pair is fifth/relative/parallel and the margin is below a threshold tuned on the project's blind songs, print "G major (or E minor)"; if the chord-cadence rule (final chord, dominant→tonic motion in the stems' bass line) picks the runner-up, swap the order; if the pair is "other", print the leader alone.
- Because the fifth error is the one the project actually hit (D for G), add a tonic-cadence check as a veto specifically against the dominant: when the leading candidate is a fifth above the runner-up and the song's last chord/bass note is the runner-up's tonic, prefer the runner-up.

### Gaps
- No paper or repo documenting a confidence-ordered fusion of yt-dlp, AcoustID and Shazam for a hobby pipeline was found; the policy above is inferred from the individual tools' documented outputs.
- No published calibration of "margin below which to hedge" exists for any of the key estimators; it must be fitted on the project's own labelled set.
