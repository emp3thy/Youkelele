## KQ1. Rhythm quantisation algorithms: naive grid snapping vs HMM/metrical models vs 2022-2026 neural MIDI-to-score

### Takeaway
Naive grid snapping (note_seq, music21, MuseScore 3 import) is deterministic and easy but cannot infer tempo, meter or tuplets on its own; the research frontier (PM2S 2022, Beyer & Dai 2024, Murgul/Heizmann 2025, Wachter et al. 2026) treats quantisation as sequence-to-sequence prediction conditioned on beats, reaching ~97% onset F1 but only ~83% note-value accuracy on piano data, and every released model is piano-trained. For a ukulele pipeline that already has audio beat times (Beat This!), beat-conditioned grid snapping with a (4,3)-style divisor set is the pragmatic baseline; tuplets/swing need explicit extra handling.

### Cited Findings

**Naive grid snapping libraries (Python)**
- note_seq `quantize_note_sequence(note_sequence, steps_per_quarter)` snaps note start/end and chord times to the nearest step; it raises `MultipleTimeSignatureError` if the time signature changes, `MultipleTempoError` if the tempo changes, `BadTimeSignatureError` for a 0 numerator or non-power-of-two denominator, and `NegativeTimeError` for negative times — [note_seq sequences_lib.py](https://github.com/magenta/note-seq/blob/main/note_seq/sequences_lib.py)
- note_seq rounding rule: `QUANTIZE_CUTOFF = 0.5`; the code comment explains "Note events before this cutoff are rounded down to nearest step. Notes above this cutoff are rounded up ... A number close to 1.0 gives less wiggle room for notes that start early, and they will be snapped to the previous step." Implementation: `int(unquantized_steps + (1 - quantize_cutoff))` — [note_seq sequences_lib.py](https://github.com/magenta/note-seq/blob/main/note_seq/sequences_lib.py)
- note_seq forces a minimum one-step note: `if note.quantized_end_step == note.quantized_start_step: note.quantized_end_step += 1` — [note_seq sequences_lib.py](https://github.com/magenta/note-seq/blob/main/note_seq/sequences_lib.py)
- note_seq `quantize_note_sequence_absolute(note_sequence, steps_per_second)` quantises on an absolute-seconds grid; "Tempos and time signatures will be copied but ignored." No swing or tuplet support exists in either function — [note_seq sequences_lib.py](https://github.com/magenta/note-seq/blob/main/note_seq/sequences_lib.py)
- note-seq's last PyPI release is 0.0.5 on 2022-07-01 (flag: effectively unmaintained for 4+ years) — [PyPI note-seq JSON](https://pypi.org/pypi/note-seq/json)
- music21 `Stream.quantize(quarterLengthDivisors=(), processOffsets=True, processDurations=True, inPlace=False, recurse=False)`: "(2,) will snap all events to eighth note grid. (4, 3) will snap events to sixteenth notes and eighth note triplets, whichever is closer. (4, 6) will snap events to sixteenth notes and sixteenth note triplets ... The default is (4, 3)." Since v7 it uses "look-ahead approach to choosing divisors to avoid gaps when processing durations" (the next note's quantized offset is considered when quantising the current duration) and records the error in `.editorial.offsetQuantizationError` and `.quarterLengthQuantizationError` — [music21 stream/base.py](https://github.com/cuthbertLab/music21/blob/master/music21/stream/base.py)
- music21 MIDI import (`midi/translate.py`) has `quantizePost: bool = True` and `quarterLengthDivisors` parameters; when quantizePost is True it calls `s.quantize(quarterLengthDivisors=...)` after import, defaulting to `defaults.quantizationQuarterLengthDivisors` — [music21 midi/translate.py](https://github.com/cuthbertLab/music21/blob/master/music21/midi/translate.py)
- music21 10.5.0 was released 2026-06-17 and requires Python >= 3.11 — [PyPI music21 JSON](https://pypi.org/pypi/music21/json)

**MuseScore MIDI import quantisation**
- MuseScore 3 quantised "by a regular grid" with a user-set MAX resolution (quarter ... 128th); "the actual quantization grid size is adaptive and reduces when the note length is small" — the max value is an upper limit per note — [musescore.org node/22017](https://musescore.org/en/node/22017)
- In MuseScore 3 the "Reduce to shortest note in bar" checkbox lowers the quantization value only if notes shorter than the chosen quantization exist, whereas the "Shortest note in bar" menu item "sets the quantization value to the minimum note duration in the bar rounded to the nearest larger power-of-two duration" — [musescore.org node/22017](https://musescore.org/en/node/22017)
- MuseScore 3 issue: "[MIDI import] Tuplet recognition confused by larger quantization settings" — [musescore.org node/22015](https://musescore.org/en/node/22015)
- MuseScore 4 handbook MIDI-import page states "MIDI import panel not currently implemented" — [MuseScore 4 handbook](https://musescore.org/en/handbook/4/midi-import)
- GitHub issue #28402 (opened 2025-06-13, still open, no maintainer response) asks for MIDI import quantisation in MuseScore Studio: "There was such a feature in MuseScore 3, but now it's gone"; the reporter wants quantisation level selection, tuplet recognition, and post-import quantisation — [musescore/MuseScore#28402](https://github.com/musescore/MuseScore/issues/28402)

**HMM / probabilistic rhythm transcription (Nakamura et al.)**
- Nakamura, Yoshii, Sagayama (SMC 2016) "Rhythm transcription of polyphonic MIDI performances based on a merged-output HMM for multiple voices": HMMs "combine a model for music scores and a model describing the temporal fluctuations in music performances"; each voice is an HMM and the polyphonic performance is the merged output; Viterbi decoding — [Nakamura SMC 2016 PDF](https://eita-nakamura.github.io/articles/Nakamura_etal_RhythmTranscriptionOfPolyphonicMIDIPerformances_SMC2016.pdf)
- Same paper: candidate note values were "All normal, dotted, and triplet note values ranging from the whole note to the 32nd note"; the note HMM produced "grammatically wrong sequences of note values, for example, triplets that appear in single or two notes without completing a unit of beat", whereas "these grammatical errors were not observed in the transcriptions by the metrical HMM" because it models beat/bar structure — [Nakamura SMC 2016 PDF](https://eita-nakamura.github.io/articles/Nakamura_etal_RhythmTranscriptionOfPolyphonicMIDIPerformances_SMC2016.pdf)
- Metrical HMM definition (from the same paper): "the note values are given as differences between successive beat positions" within a bar; "Incorporation of the metre structure is an advantage of metrical HMMs" — [Nakamura SMC 2016 PDF](https://eita-nakamura.github.io/articles/Nakamura_etal_RhythmTranscriptionOfPolyphonicMIDIPerformances_SMC2016.pdf)
- Journal version (IEEE/ACM TASLP, arXiv 2017-01-29): the merged-output HMM "outperformed other methods by more than 12 points in the accuracy for polyrhythmic performances" and the authors state source code is publicly available — [arXiv 1701.08343](https://arxiv.org/abs/1701.08343)
- Nakamura's homepage lists an audio-to-score transcription demo (https://audio2score.github.io/), the MUSTER evaluation metric site (https://amtevaluation.github.io/) and a MIDI alignment tool (https://midialignment.github.io/), but no download/platform/licence details for a standalone rhythm quantiser were visible — [eita-nakamura.github.io](https://eita-nakamura.github.io/)
- Nakamura's metrical HMM generative description: onset score times, local tempos and onset times, with onset score times from a Markov model — [arXiv 2008.12710 (Non-local musical statistics)](https://arxiv.org/pdf/2008.12710)

**Neural performance-MIDI-to-score (2022-2026)**
- Liu, Kong, Morfi, Benetos (ISMIR 2022) "Performance MIDI-to-Score Conversion by Neural Beat Tracking": "a MIDI-to-score quantisation method using a convolutional-recurrent neural network (CRNN) trained on MIDI note sequences to predict whether notes are on beats", then extended "to predict the quantised times for all beat and non-beat notes" plus "key signatures, time signatures, and hand parts"; evaluated with MV2H against two commercial products; toolbox at https://github.com/cheriell/PM2S — [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf)
- PM2S inserts "out-of-note beats" between detected in-note beats (K in {0,1,2,3} extra beats per interval) chosen to minimise an objective O1 = sum |log((b_{n+2}-b_{n+1})/(b_{n+1}-b_n))| — i.e. the tempo-change cost — so beats are hypothesised even where no note falls on them — [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf)
- PM2S training data: MAPS (ENSTDkCl real-recording subset) with A-MAPS metrical annotations, Classical Piano-Midi (CPM), and ASAP; piece-level splits via ACPAS; the authors note the ASAP MIDI scores "were written by non-professionals and are not a good source of ground truth" so they use the .tsv annotations — [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf)
- PM2S repo: sub-models for beat/downbeat tracking, note quantisation, time signature, key signature and hand part; requires Python 3.8 and PyTorch 1.12.0; MIT licence; pre-trained model used via `demo.ipynb` — [cheriell/PM2S](https://github.com/cheriell/PM2S)
- Beyer & Dai (ISMIR 2024, arXiv 2024-09-30) "End-to-end Piano Performance-MIDI to Score Conversion with Transformers": sequence-to-sequence translation "rather than note-wise classification"; compound tokens "carefully quantize continuous values" and cut sequence length 3.5x; first to predict "trill marks or stem direction"; "significant improvements over previous deep learning approaches and complex HMM-based state-of-the-art pipelines" on MUSTER; code https://github.com/TimFelixBeyer/MIDI2ScoreTransformer — [arXiv 2410.00210](https://arxiv.org/abs/2410.00210)
- MIDI2ScoreTransformer repo: pre-trained `MIDI2ScoreTF.ckpt` in Releases; Python 3.11; depends on a modified music21, `score_transformer`, `muster`, and a MuseScore binary path in `constants.py`; piano-only; requires ASAP (with fixes) and ACPAS metadata to reproduce — [TimFelixBeyer/MIDI2ScoreTransformer](https://github.com/TimFelixBeyer/MIDI2ScoreTransformer)
- Murgul & Heizmann (SMC 2025, arXiv 2025-07-01) "Beat and Downbeat Tracking in Performance MIDI Using an End-to-End Transformer Architecture": encoder-decoder transformer translating MIDI tokens to beat annotations; trained/evaluated on A-MAPS, ASAP, GuitarSet and Leduc; "outperforms existing symbolic music beat tracking approaches" (HMM and DL baselines); uses dynamic augmentation and tokenisation tricks — [arXiv 2507.00466](https://arxiv.org/abs/2507.00466)
- Wachter, Murgul, Heizmann (ICSM 2025; arXiv submitted 2026-04-24) "Transformer-Based Rhythm Quantization of Performance MIDI Using Beat Annotations": T5-based model taking performance MIDI plus beat information, with "beat-based pre-quantization alignment"; on ASAP reports onset F1 97.3% and note value accuracy 83.3%; "generalizes well across time signatures, including those not seen during training"; abstract does not mention tuplets, swing or code — [arXiv 2604.22290](https://arxiv.org/abs/2604.22290)
- A 2018 ICASSP paper by the Nakamura group integrates multi-pitch detection and rhythm quantisation ("Towards Complete Polyphonic Music Transcription") — [ICASSP 2018 PDF](https://eita-nakamura.github.io/articles/AudioAndMIDITranscription_ICASSP2018.pdf)

### Inferences
- All public neural MIDI-to-score models (PM2S, MIDI2ScoreTransformer, the Murgul/Heizmann/Wachter models) are trained on classical piano (ASAP/A-MAPS/CPM); only Murgul & Heizmann 2025 trained on guitar data (GuitarSet, Leduc). None is ukulele-aware; applying them to a strummed-ukulele or pop-guitar MIDI is out of distribution.
- The Wachter et al. 2026 design (beat annotations as an input, then quantisation) matches the proposed pipeline (Beat This! beats + Basic Pitch notes) structurally, which argues for a two-stage design: audio beat/downbeat grid first, then snap/infer note values relative to that grid.
- music21's divisor-set approach `(4, 3)` or `(4, 6)` is the only off-the-shelf Python quantiser that handles triplets; note_seq cannot. Swing is not natively modelled by any of the Python libraries found; the usual approach is to quantise to a triplet grid (divisor 3 or 6) and re-notate as straight eighths with a swing marking (this is an inference from the music21 docs, not a documented feature).
- The note_seq `quantize_cutoff` parameter is the only exposed "early-note bias" knob among the libraries; a value above 0.5 biases early (anticipated) strums back to the previous grid line, which is relevant for pushed strums.
- 83.3% note-value accuracy even on the best 2026 model vs 97% onset accuracy confirms that duration/offset quantisation is the weak step; for tab (where sustain is rarely notated precisely) prioritising onset quantisation is defensible.

### Gaps
- Cemgil & Kappen "Monte Carlo methods for tempo tracking and rhythm quantization" (JAIR 2003) and Raphael "Automated rhythm transcription" (ISMIR 2001): the JAIR URL I tried resolved to a different article and Semantic Scholar/dblp rate-limited; I could not fetch primary text, so no cited findings. Known to the field as the Bayesian switching-Kalman tempo-tracking lineage, but unverified here.
- Code availability for Wachter et al. 2026 and Murgul & Heizmann 2025 is not stated on the arXiv abstract pages.
- No reliable source found on how Beyer & Dai or Wachter handle tuplets or swing explicitly.
- MuseScore 3 handbook page for MIDI import now redirects to the MuseScore 4 handbook, and musescore.org forum nodes return a JS challenge to scripted fetches; the option list (Human performance, Simplify durations, Show staccato, Detect swing, Recognize pickup measure) could not be re-verified from the handbook text.

## KQ2. Note duration cleanup (Basic Pitch offsets, minimum durations, merging, ghost notes, rests vs sustain, legato vs staccato for ukulele)

### Takeaway
Basic Pitch note offsets are driven by a frame-activation threshold and are systematically early (one third-party measurement found 50-68% silence in transcribed stems); the library's own defaults (onset 0.5, frame 0.3, min note 127.7 ms) and the "legato-extend to next onset with a gap cap" post-process used by downstream projects are the concrete levers. Basic Pitch MIDI timing is absolute seconds with a header tempo that does not affect note timing.

### Cited Findings
- Basic Pitch `predict()` defaults: `DEFAULT_ONSET_THRESHOLD = 0.5`, `DEFAULT_FRAME_THRESHOLD = 0.3`, `DEFAULT_MINIMUM_NOTE_LENGTH_MS = 127.7`, `DEFAULT_MINIMUM_MIDI_TEMPO = 120`; docstrings: "onset_threshold: Minimum energy required for an onset to be considered present", "frame_threshold: Minimum energy requirement for a frame to be considered present", "minimum_note_length: The minimum allowed note length in milliseconds", `melodia_trick=True` "Use the melodia post-processing step", `multiple_pitch_bends=False` — [basic_pitch/inference.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/inference.py)
- Frame geometry: `AUDIO_SAMPLE_RATE = 22050`, `FFT_HOP = 256`, so `ANNOTATIONS_FPS = 22050 // 256` (= 86 fps, ~11.6 ms/frame); `min_note_len` is computed as `round(minimum_note_length/1000 * (AUDIO_SAMPLE_RATE/FFT_HOP))` (127.7 ms -> 11 frames, the `min_note_len: int = 11` default in `model_output_to_notes`) — [basic_pitch/constants.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/constants.py), [basic_pitch/inference.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/inference.py), [basic_pitch/note_creation.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/note_creation.py)
- Offset rule in `output_to_notes_polyphonic`: a note continues while frames stay above `frame_thresh`, tolerating up to `energy_tol: int = 11` consecutive below-threshold frames ("Drop notes below this energy"); notes with `i - note_start_idx <= min_note_len` are discarded; the `melodia_trick` pass then adds extra notes from remaining frame energy, again dropping those shorter than `min_note_len` — [basic_pitch/note_creation.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/note_creation.py)
- MIDI writing: `note_events_to_midi(..., midi_tempo)` creates `pretty_midi.PrettyMIDI(initial_tempo=midi_tempo)`; PR #193 (2026-05-29, open, docs only, closes issue #152 from 2024-11-18) states that `midi_tempo` "is only passed to pretty_midi.PrettyMIDI(initial_tempo=...), which writes the tempo into the MIDI header. Note start/end times come from the audio in absolute seconds and are never rescaled" — [spotify/basic-pitch PR #193](https://github.com/spotify/basic-pitch/pull/193), [issue #152](https://github.com/spotify/basic-pitch/issues/152), [basic_pitch/note_creation.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/note_creation.py)
- Issue #190 (2026-04-15): the frame-level `model_output["note"]` array has growing temporal drift (-2.7 s by the end of a ~530 s file) because of a 188-sample mismatch between kept frames x FFT_HOP (36,352) and the actual hop (36,164); "The note-level output (note_events, midi_data) is not affected because it is decoded from seconds-stamped onset/offset detections" — [spotify/basic-pitch issue #190](https://github.com/spotify/basic-pitch/issues/190)
- Third-party measurement (Coming Undone project, docs updated through Sept 2026): Basic Pitch "ends a note when frame activation drops below frame_threshold (default 0.3), which is well before the note stops sounding"; on their test track the bass stem was 68% silence and the melody stem 50% silence. Their fix: optional `--legato` that extends each note to the next onset, capped by `legato_max_gap_beats` (default 0.25, roughly a sixteenth) "to avoid collapsing intentional rests into sustain"; plus a cleanup pass with a velocity floor (drop velocity < 15), de-overlap, and a duration cap (default 2 beats) — [swwallowws/coming-undone](https://github.com/swwallowws/coming-undone)
- Basic Pitch packaging: v0.4.0 released 2024-08-16 (latest); `tensorflow>=2.4.1,<2.15.1` on non-mac; `onnxruntime` is the Windows backend for Python < 3.11; `tflite-runtime` only on Linux; README claims support for Python 3.7-3.11 on macOS/Windows/Ubuntu; open issues in 2026 ask for Python 3.12 / Keras 3 support and an onnxruntime fallback on 3.12+ — [basic-pitch pyproject.toml](https://github.com/spotify/basic-pitch/blob/main/pyproject.toml), [spotify/basic-pitch README](https://github.com/spotify/basic-pitch), [GitHub issues search](https://api.github.com/search/issues?q=repo:spotify/basic-pitch+duration)
- pretty_midi `remove_invalid_notes()` "Removes any notes whose end time is before or at their start time" (per instrument) — [pretty_midi/pretty_midi.py](https://github.com/craffel/pretty-midi/blob/main/pretty_midi/pretty_midi.py)
- OpenUkulele (ukulele tab generator built on Basic Pitch) documents that "Basic Pitch may drop notes, misidentify pitches, or place bass outside ukulele range; such measures are reported as non-arrangeable rather than silently transposed", and recommends "30-60 second single-voice recordings in quiet environments with melody in the C4-C6 range" — [xin-pu/OpenUkulele](https://github.com/xin-pu/OpenUkulele)
- The merged-output-HMM authors note "Recognition of offsets and articulations and detection of ornaments are challenging problems" left for future work — [Nakamura SMC 2016 PDF](https://eita-nakamura.github.io/articles/Nakamura_etal_RhythmTranscriptionOfPolyphonicMIDIPerformances_SMC2016.pdf)

### Inferences
- For strummed ukulele, Basic Pitch offsets should be treated as unreliable and discarded in favour of a rule: sustain each note/chord to the next onset on the same string-group (legato by default), cut to a rest only when the inter-onset gap exceeds a cap such as the Coming Undone 0.25-beat setting, and emit staccato only if the detected duration is below roughly a third of the inter-onset interval. This is a design inference, not a sourced recipe.
- Raising `frame_threshold` shortens notes further and lowering it lengthens them; `energy_tol` (11 frames = ~128 ms) is the hidden gap-bridging parameter that is not exposed in `predict()` and would need a patched call to `output_to_notes_polyphonic`.
- `minimum_note_length` (127.7 ms) is already close to a 16th note at 117 bpm, so fast strums at the 16th level may be dropped at default settings; lowering it to ~60-80 ms is a reasonable experiment for strum detection (inference).
- Octave errors and ghost notes: no Basic Pitch-specific octave-error study was found; the practical filters used by downstream projects are velocity floors, duration caps, range clipping to the instrument (ukulele C4-A5 open-string range plus 12-15 frets), and de-overlap.

### Gaps
- No quantitative Basic Pitch offset-accuracy numbers (e.g., note-with-offset F1 on GuitarSet) were found in the fetched sources; the 50-68% silence figure is a single informal measurement.
- No published guidance specific to legato/staccato decisions for ukulele notation was found.
- GitHub issue search on basic-pitch for "duration/offset/staccato/legato" returned no issue dedicated to offset accuracy; the problem appears mostly in downstream projects rather than upstream issues.

## KQ3. Time signature detection, pickup bars, first downbeat, hypermeter, tempo changes/ritardando

### Takeaway
No off-the-shelf Python tool infers time signature from audio beat/downbeat output; madmom's DBN enumerates candidate `beats_per_bar` (default [3, 4] in Beat This!'s optional DBN mode), Beat This! itself outputs only beat and downbeat times, and PM2S/Beyer & Dai predict time signature from MIDI notes (piano-trained). Pickup bars fall out of downbeat tracking (first downbeat is simply not at the first note); dedicated anacrusis or hypermeter detectors were not found.

### Cited Findings
- Beat This! "does not output time signature or explicit tempo values" and "performs worse on continuity metrics (CMLt, AMLt) compared to DBN-based approaches"; the authors "acknowledge the system can still fail, especially for difficult and underrepresented genres", with beat F1 77.1 on classical — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658)
- Beat This! optional DBN postprocessing (`dbn=True`) uses madmom's `DBNDownBeatTrackingProcessor` with `beats_per_bar=[3, 4]`, `min_bpm=55.0`, `max_bpm=215.0`, `fps=50` — [beat_this/model/postprocessor.py](https://github.com/CpJKU/beat_this/blob/main/beat_this/model/postprocessor.py)
- madmom `DBNDownBeatTrackingProcessor(beats_per_bar, min_bpm=55., max_bpm=215., num_tempi=60, transition_lambda=100, observation_lambda=16, threshold=0.05, correct=True, fps)`: `beats_per_bar` "Can be either a single number or a list or array with bar lengths (in beats)"; `transition_lambda` is "Lambda for the exponential tempo change distribution (higher values prefer a constant tempo from one beat to the next one)"; output is an array of (time in seconds, position inside bar starting at 1) — [madmom/features/downbeats.py](https://github.com/CPJKU/madmom/blob/main/madmom/features/downbeats.py)
- madmom on PyPI is 0.16.1 from 2018-11-14 and "only supports Python<3.10 and numpy<1.20"; Beat This! instructs installing madmom from GitHub (`pip install git+https://github.com/CPJKU/madmom.git`); madmom's last GitHub commit was 2024-08-25 (flag: dormant) — [PyPI madmom JSON](https://pypi.org/pypi/madmom/json), [beat_this README](https://github.com/CpJKU/beat_this), [GitHub commits API](https://api.github.com/repos/CPJKU/madmom/commits?per_page=1)
- "The SMC Blind Spot" (arXiv 2026-05-12): "the standard DBN's default minimum tempo of 55 BPM prevents it from inferring the correct tempo for 21% of SMC tracks, forcing double-tempo predictions on slow music"; failure modes are octave errors, continuity errors and complete failure; models produce "confident-but-wrong activations"; remedies proposed: training-data diversification and multi-hypothesis tempo estimation — [arXiv 2605.12287](https://arxiv.org/abs/2605.12287)
- "Skip That Beat" (Morais, McFee, Fuentes; LAMIR 2025, arXiv 2025-02-18): data augmentation "by removing beat intervals from 4/4 annotated tracks" to synthesise 2/4 and 3/4 training data; "helps to improve downbeat tracking for underrepresented meters while preserving the overall performance of beat tracking" — [arXiv 2502.12972](https://arxiv.org/abs/2502.12972)
- "Masked diffusion enables coherent beat tracking" (Foscarin, Korzeniowski, Vogl; ISMIR 2026, arXiv 2026-08-05): neural beat trackers "produce invalid outputs, such as consecutive downbeats and erratic tempo changes"; iterative masked-diffusion inference "reduces erratic behaviours and improves beat-tracking performance" — [arXiv 2608.04624](https://arxiv.org/abs/2608.04624)
- Time-signature detection survey (Abimbola, Kostrzewa, Kasprowski; Sensors 2021, DOI 10.3390/s21196494): reviews "More than 110 publications" from 2003 onward on time signature estimation "from different types of input signals (audio and MIDI)", split into classical and deep-learning methods — [Semantic Scholar record](https://api.semanticscholar.org/graph/v1/paper/search?query=time+signature+estimation+symbolic+MIDI+meter) (the MDPI page itself returned HTTP 403 to fetches)
- PM2S predicts time signatures (and key signatures and hand parts) jointly with beat positions from MIDI notes — [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf), [cheriell/PM2S](https://github.com/cheriell/PM2S)
- Wachter et al. 2026 claim generalisation "across time signatures, including those not seen during training" — [arXiv 2604.22290](https://arxiv.org/abs/2604.22290)
- pretty_midi `get_beats(start_time=0.)`: "For compound meters (any whose numerator is a multiple of 3 greater than 3), this method returns every third denominator note (for 6/8 ... every third 8th note). For all other meters ... every denominator note"; `get_downbeats()` inserts a 4/4 signature at `start_time` "If there are no time signatures or they start after 0s"; `estimate_beat_start(candidates=10, tolerance=.025)` picks "which of the first few onsets results in the best correlation with the onset spike train" — [pretty_midi/pretty_midi.py](https://github.com/craffel/pretty-midi/blob/main/pretty_midi/pretty_midi.py)
- ASAP dataset (piano): 236 scores, 1067 performances, >92 h; annotations include downbeats, beats, time-signature and key-signature changes, in TSV/JSON; beat labels are "db" (downbeat), "b" (beat) and "bR" for beats where "standard notation rules are not followed"; CC BY-NC-SA 4.0 (non-commercial) — [fosfrancesco/asap-dataset](https://github.com/fosfrancesco/asap-dataset)
- Beat This! training-data annotations are in a separate repo (`beat_this_annotations`, v1.0 for exact paper results) — [beat_this README](https://github.com/CpJKU/beat_this)

### Inferences
- Practical time-signature inference from Beat This! output: count beats between consecutive downbeats; the mode of that count over the song gives beats-per-bar (3 vs 4); 6/8 vs 3/4 and 12/8 vs 4/4 are ambiguous at the beat level because Beat This!/madmom track the tactus, so distinguishing them requires an onset-level subdivision test (are inter-beat onsets predominantly in thirds or halves?). This is an inference; no tool found does it.
- Running the madmom DBN with `beats_per_bar=[2, 3, 4]` (or [3, 4, 6]) on Beat This! activations is the only ready-made way to get a globally consistent bar hypothesis, at the cost of the DBN's 55-215 bpm tempo prior (the "SMC blind spot" failure on slow music).
- Pickup/anacrusis: with downbeat tracking the first downbeat time is simply the first "db"; notes before it belong to a pickup bar whose length is (first downbeat time - first note time) expressed in beats. ASAP's "bR" convention shows that even human annotators flag irregular opening beats.
- Hypermeter (4/8-bar phrasing): nothing found; a downbeat-level autocorrelation of onset density or chord-change positions at lags of 4 and 8 bars is the obvious heuristic but is unsourced.
- Ritardando at song endings: Beat This! (no DBN) follows the activations and so tracks slowdowns but can produce erratic tempo; the masked-diffusion ISMIR 2026 model is explicitly aimed at this. If Beat This! beats are used as the grid, the tab inherits the ritardando as unequal bar durations, which is correct for playback sync but should be flattened to a nominal tempo for notation.

### Gaps
- No paper or tool specifically about anacrusis/pickup-bar detection was found (Semantic Scholar and Bing searches returned nothing relevant).
- No source on hypermeter/phrase-level (4/8-bar) inference was found.
- The MDPI survey's numerical accuracies for 3/4 vs 4/4 vs 6/8 could not be read (HTTP 403).
- No source found on how Guitar Pro / MuseScore detect pickup measures on MIDI import (MuseScore 3 had a "Recognize pickup measure" option per the handbook, but the page could not be retrieved).

## KQ4. Beat grid from Beat This! / madmom: beat times -> bar/beat/subdivision grid; gap before first downbeat; locking to the video clock

### Takeaway
Beat This! returns beat and downbeat times in seconds at 50 fps resolution (20 ms frames, peaks picked within +/-70 ms, probability > 0.5, downbeats snapped to the nearest beat); a bar/beat/subdivision grid is built by indexing beats from each downbeat and linearly subdividing inter-beat intervals. Everything is relative to the decoded audio's t=0, so video-clock locking depends only on extracting audio without trimming.

### Cited Findings
- Beat This! minimal postprocessing: select "all frames assigned the highest beat/downbeat probability within a neighborhood of +/-3 frames (+/-70 ms), and probability > 0.5", then downbeats "are moved to align with the nearest beat prediction"; spectrogram at 50 fps (hop 441 samples at 22.05 kHz) — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658); `Postprocessor(type="minimal", fps=50)`; `beat_time = beat_frame / self.fps` — [beat_this/model/postprocessor.py](https://github.com/CpJKU/beat_this/blob/main/beat_this/model/postprocessor.py)
- Beat This! GTZAN results: beat F1 89.1 +/- 0.3, downbeat F1 78.3 +/- 0.4; shift-tolerant loss uses a 7-frame max-pool so "only the largest positive prediction +/-3 frames from each label is considered" — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658)
- Python API: `File2Beats(checkpoint_path="final0", device="cuda", dbn=False)`; `beats, downbeats = file2beats(audio_path)`; `Audio2Beats` for in-memory tensors; `Audio2Frames` for framewise logits; `save_beat_tsv` writes a Sonic Visualiser-compatible .beats file; models: `final0-2` (~78 MB), `small0-2` (~8.1 MB); requires PyTorch >= 2.0, `tqdm einops soxr rotary-embedding-torch`, ffmpeg for non-wav; `--float16` and `--gpu=-1` CLI flags — [beat_this README](https://github.com/CpJKU/beat_this)
- beat-this 1.1.0 on PyPI 2026-04-14; last commit 2026-05-28 (actively maintained) — [PyPI beat-this JSON](https://pypi.org/pypi/beat-this/json), [GitHub commits API](https://api.github.com/repos/CpJKU/beat_this/commits?per_page=1)
- Beat This! warns results are "unfairly good" on any file from its training datasets (everything except GTZAN) — [beat_this README](https://github.com/CpJKU/beat_this)
- mir_eval beat metrics: `f_measure(..., f_measure_threshold=0.07)` (70 ms), `continuity(..., continuity_phase_threshold=0.175, continuity_period_threshold=0.175)`, `trim_beats(beats, min_beat_time=5.0)` (first 5 s ignored) — [mir_eval/beat.py](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/beat.py)
- madmom DBN output format: "The position inside the bar follows the natural counting and starts at 1", e.g. `[[0.09, 1.], [0.45, 2.], ...]` — [madmom/features/downbeats.py](https://github.com/CPJKU/madmom/blob/main/madmom/features/downbeats.py)
- Coming Undone's approach: "Beat/bar alignment uses fitted constant-tempo grids or tempo maps for variable-tempo material, with per-track latency measured against detected grid positions" — [swwallowws/coming-undone](https://github.com/swwallowws/coming-undone)
- PM2S's beat-interval regularisation objective (minimise |log of ratio of successive beat intervals|) is a documented way to fill missing beats in a sparse beat list — [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf)
- ReaBeat (REAPER extension) and a C++ port and Rust crate of Beat This! exist, showing the model is used for DAW tempo-map generation — [b451c/ReaBeat](https://github.com/b451c/ReaBeat), [mosynthkey/beat_this_cpp](https://github.com/mosynthkey/beat_this_cpp), [crates.io beat-this](https://crates.io/crates/beat-this)

### Inferences
- Grid construction (inference from the APIs above): (1) for each downbeat d_k, beats-per-bar = number of beats in [d_k, d_{k+1}); (2) beat index within bar = position in that list; (3) subdivisions = linear interpolation between consecutive beat times (for 8ths, 16ths or triplets); (4) notes before the first downbeat form a pickup; (5) fill gaps where Beat This! dropped a beat using a PM2S-style interval-ratio check (a beat interval ~2x its neighbours implies a missed beat).
- The 20 ms frame grid plus the 70 ms peak neighbourhood means Beat This! beat times carry roughly +/-20 ms quantisation jitter; at 120 bpm a 16th note is 125 ms, so beat jitter is ~1/6 of a 16th and acceptable for 8th/16th-level strum patterns, but subdivisions should be interpolated from smoothed beat times (e.g., local linear regression over 2-4 beats) rather than raw peaks.
- Video-clock locking: Beat This! times are offsets from sample 0 of the decoded audio; as long as the audio is extracted from the video container without trimming or resampling-induced offset, t_video = t_audio. Any lead-in (silence or speech) is simply part of the timeline, and the first downbeat time is the anchor. No source discusses yt-dlp/ffmpeg extraction offsets, so this is unverified.
- Because Beat This! has no tempo prior, it is more likely than madmom's DBN to follow a live performance's drift and ritardando, but also more likely to produce isolated spurious or missing beats (its weaker CMLt/AMLt); a light post-filter (reject beat intervals outside 0.6-1.6x the local median) is advisable.

### Gaps
- No source on aligning extracted-audio timestamps to YouTube player time (container start offsets, priming samples); must be verified empirically.
- No published comparison of Beat This! vs madmom on pop/folk ukulele recordings or old/live recordings with tempo drift.

- OpenUkulele assumes "high G re-entrant" tuning (G4-C4-E4-A4, 15 frets), "explicitly rejecting linear guitar-style assumptions. Low G variants are noted as future work" — [xin-pu/OpenUkulele](https://github.com/xin-pu/OpenUkulele)
- Ukulizer (Zuthen) is a Node.js/web "Converter of tablature from guitar to ukulele", last pushed 2022-03-12 (flag: dormant; algorithm not documented in README) — [Zuthen/Ukulizer](https://github.com/Zuthen/Ukulizer), [GitHub repo search](https://api.github.com/search/repositories?q=ukulele+tablature)

### Inferences
- Guitar-tab-to-ukulele mapping (from the capo-5 identity): guitar string 1-4 (E B G D) -> ukulele A E C G with fret_uke = fret_guitar - 5; frets 0-4 on guitar strings 1-4 and anything on strings 5-6 (A, E) have no direct equivalent and must be re-fingered (transpose up an octave, move to another string, or drop). With high-G re-entrant tuning the 4th string sounds an octave above the guitar D-string equivalent, so bass-line notes on the uke 4th string will invert; OpenUkulele's "voice conflict" and range validation is the only found implementation addressing this.
- Pitch-range gate for ukulele (inference from GCEA + 12-15 frets): roughly C4 (MIDI 60) to C6/D6 (MIDI 84-86) with high-G; a MIDI track whose notes fall mostly below MIDI 55 is a bass/low-guitar part needing octave transposition.
- Recommended identification heuristic (inference combining the sources): prefer tracks whose GM program is 24-31 (guitar) or 0-7 (piano) with a track name containing "guitar", "uke", "melody", "vocal", "lead"; skip channel 9; for the melody choose the non-drum track with highest mean pitch and lowest polyphony (notes per onset ~1); for chords choose the track with polyphony >= 3 and the most regular onset spacing. midi-miner can replace this with a learned classifier but its model is a Google-Drive download of unknown provenance.
- For type-0 files everything is on one track, so instruments must be separated by channel/program (pretty_midi already does this by keying instruments on program+channel+drum flag).
- Guitar Pro files carry string/fret, tuplets and time signatures natively, so the MIDI-quantisation stage is skipped entirely for .gp3/.gp4/.gp5 input; for .gpx/.gp (GP6-8) a conversion step (Guitar Pro or TuxGuitar export to .gp5) is required unless PyGuitarPro 0.11's GP6+ support is confirmed.

### Gaps
- Could not confirm from a release note or changelog whether PyGuitarPro 0.11 reads GP6/7/8; the two 2026 issues are closed but the README was not updated. Verify by `guitarpro.parse("file.gp")` in a venv.
- No source for GM2's Ukulele patch (it exists in the GM2 spec as a nylon-guitar bank variation, but I could not fetch a page stating it; treat as unverified).

- No source on how Guitar Pro's own MIDI export lays out tracks/channels (e.g., whether each GP track becomes a MIDI track with program change), which matters when a user supplies a GP-exported .mid rather than the .gp5.

## KQ6. Symbolic MIDI-to-tab tools that take quantised MIDI (Fretting-Transformer, open-fret, Tayuya, ukulele-aware tools)

### Takeaway
The academic state of the art (Fretting-Transformer ICMC 2025; MIDI-to-Tab ISMIR 2024) is guitar-only and trained on DadaGP-style tab tokens; the only ukulele-specific open-source tool found is OpenUkulele (Sept 2026, proof-of-concept, GCEA high-G, DP fingering with playability validation, GP5 export). open-fret is a 7-commit MIT reimplementation of Fretting-Transformer; Tayuya is dormant, solo-only, standard guitar tuning.

### Cited Findings
- Fretting-Transformer (Hamberger, Murgul, Heizmann; ICMC 2025; arXiv 2025-06): "encoder-decoder model that utilizes a T5 transformer architecture to automate the transcription of MIDI sequences into guitar tablature", "symbolic translation problem"; datasets DadaGP, GuitarToday, Leduc; "tuning/capo conditioning further enhances the model's performance"; tab accuracy 98.41% (GuitarToday), 72.19% (Leduc), 81.58% (DadaGP) in standard tuning; "surpasses baseline methods like A* and commercial applications like Guitar Pro"; no code link on the abstract page — [arXiv 2506.14223](https://arxiv.org/abs/2506.14223), [Emergent Mind summary](https://www.emergentmind.com/topics/fretting-transformer-model)
- MIDI-to-Tab (Edwards, Riley, Sarmento, Dixon; ISMIR 2024; arXiv 2024-08-09): "encoder-decoder Transformer model in a masked language modeling paradigm" assigning string/fret per note; pre-trained on DadaGP (>25,000 tablatures), fine-tuned on professional transcriptions; evaluated by a guitarist user study on four-bar excerpts — [arXiv 2408.05024](https://arxiv.org/abs/2408.05024)
- Kaliakatsos-Papakostas et al. (SMC 2022, arXiv posted 2025-10-12) "A Machine Learning Approach for MIDI to Guitar Tablature Conversion": ML string/fret assignment with playability and finger-stretch assumptions, augmented with artificial non-guitar-idiomatic data; "only standard 6-string guitar tuning is examined" — [arXiv 2510.10619](https://arxiv.org/abs/2510.10619)
- open-fret (Sidmaz666; pushed 2026-02-14; 6 stars; 7 commits; MIT): reimplements Fretting-Transformer as a "T5-Tiny-Tab" (3 encoder/3 decoder layers, 128-d, 4 heads), WordLevel tokenizer, trained on ~188k GuitarPro tracks from the `vladsavelyev/guitar_tab` corpus; outputs ASCII tab only; custom tunings/capo via prefix conditioning marked work-in-progress; Python 3.8+, PyTorch, HF Transformers; no ukulele support; roadmap lists unfinished neighbour search and technique layers — [Sidmaz666/open-fret](https://github.com/Sidmaz666/open-fret)
- Tayuya: "Python library to generate guitar tabs from MIDI files"; pipeline = extract notes from a chosen track -> note names -> detect scale -> choose fretboard positions using that scale; "supports only standard guitar tuning (E A D G B E)"; "Designed exclusively for guitar solos; chord rendering isn't implemented"; depends on mido and music21; MIT; 10 commits, dormant — [vipul-sharma20/tayuya](https://github.com/vipul-sharma20/tayuya)
- OpenUkulele (xin-pu; pushed 2026-09-14; MIT; Python 3.11+; 33 commits; "proof of concept"; 120+ tests): pipeline = MIDI or audio input -> Basic Pitch (audio) -> note events/measures with tempo and time signature -> difficulty-specific note retention -> per-measure dynamic-programming string/fret assignment -> independent playability validation (voice conflicts, range, hand span, barring, finger occupancy) -> fallback simplification (drop harmony, then bass, keep melody) -> ASCII tab, GP5 (PyGuitarPro), JSON report, optional PNG/PDF (matplotlib). Easy mode: melody + beat-1/3 bass, frets 0-5, max 2 voices, span <= 4 frets, no barring, 1/8 grid; Hard mode: melody + bass + 2 harmony voices, frets 0-15, span <= 5, barring allowed, 1/16 grid "if source permits". Experimental .NET 10 WPF GUI — [xin-pu/OpenUkulele](https://github.com/xin-pu/OpenUkulele)
- ChooseGuitar (Sibivan; pushed 2026-09-07; no licence stated): MIDI -> guitar tab + GP5; configurable `grid_step` (whole to 32nd) with independent quantisation of starts and durations, "regular and triplet patterns"; string/fret search ranked by "string movement, fret distance, chord consistency, and note duration" with backtracking when no placement fits; instrument presets in JSON define tuning as string-to-MIDI maps, fret ranges, open-string use and chord fret-distance constraints (so a 4-string GCEA preset is plausible but not shipped) — [Sibivan/ChooseGuitar](https://github.com/Sibivan/ChooseGuitar)
- GitHub repository search (2026-10-01) also surfaced: `VanKyle00/band-transcriber` (song/YouTube -> stems -> sheet music, tabs, MIDI/MusicXML; pushed 2026-06-18, 0 stars), `Dheirav/UkuleleTabsMaker` (reads tab off YouTube tutorial video frames; pushed 2026-09-21), `trevortabaka/pyuke` (notes/chords -> uke tab; 2013), `Guitarbum722/go-tabs` (Go; guitar/bass/ukulele tab API; 2017) — [GitHub search API](https://api.github.com/search/repositories?q=ukulele+tablature)

### Inferences
- None of the transformer tab models take tempo or bar structure as input; they map note pitch sequences (with DadaGP-style duration tokens) to string/fret, so they can run after quantisation and are indifferent to it. For ukulele the practical options are (a) OpenUkulele's DP+validation approach, (b) ChooseGuitar's preset-driven backtracking with a custom 4-string preset, or (c) fine-tuning open-fret/Fretting-Transformer with a GCEA tuning prefix, which has no training data (no public ukulele tab corpus was found).
- The Fretting-Transformer accuracy drop from 98% (GuitarToday, simple) to 72% (Leduc, jazz chord-melody) indicates chordal/polyphonic material is where string assignment is hard; strummed ukulele chords are better handled by chord-shape lookup than per-note models (inference).

- No public ukulele tablature dataset (DadaGP contains guitar/bass; ukulele tracks in GP files are rare and "rare combinations of instruments and tunings may not be supported" by the DadaGP encoder).
- Fretting-Transformer official code: not linked from arXiv; unclear whether it was released.
- GuitarToday and Leduc dataset licensing not checked.

## KQ7. What tempo/timing precision is "good enough" for strum patterns at the 8th/16th level?

### Takeaway
The MIR convention is a +/-70 ms beat tolerance; Beat This! quantises to 20 ms frames and Basic Pitch to 11.6 ms frames; a 16th note at 120 bpm is 125 ms wide, so grid half-widths of ~62 ms are the budget, meaning raw Beat This! beats are adequate for 8th-level strums and borderline for 16ths unless beat times are smoothed. Perceptual JND literature exists (Friberg & Sundberg 1995) but its numbers could not be retrieved here.

### Cited Findings
- mir_eval beat F-measure tolerance is 0.07 s; continuity metrics use 17.5% phase and period thresholds — [mir_eval/beat.py](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/beat.py); Beat This! and PM2S both evaluate at +/-70 ms — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658), [ISMIR 2022 paper PDF](https://archives.ismir.net/ismir2022/paper/000047.pdf)
- Beat This! frame rate 50 fps (20 ms); peak picking in +/-3 frames (+/-70 ms) — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658)
- Basic Pitch frame hop 256 samples at 22,050 Hz (~11.6 ms); minimum note length default 127.7 ms (11 frames) — [basic_pitch/constants.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/constants.py), [basic_pitch/inference.py](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/inference.py)
- pretty_midi `estimate_beat_start` treats an onset within 25 ms (`tolerance=.025`) of a beat as on-beat — [pretty_midi/pretty_midi.py](https://github.com/craffel/pretty-midi/blob/main/pretty_midi/pretty_midi.py)
- Beat This! shift-tolerant training considers predictions within +/-3 frames (+/-60 ms at 50 fps; paper says +/-70 ms) of a label as correct, so the model is not trained to be more precise than that — [arXiv 2407.21658 HTML](https://arxiv.org/html/2407.21658)
- Coming Undone's legato gap cap of 0.25 beat and its practice of measuring "per-track latency ... against detected grid positions" (i.e. a constant offset between transcriber onsets and the beat grid) — [swwallowws/coming-undone](https://github.com/swwallowws/coming-undone)
- Friberg & Sundberg, "Time discrimination in a monotonic, isochronous sequence", JASA 98(5):2524 (1995), DOI 10.1121/1.413218, 252 citations per Semantic Scholar — the canonical JND reference; the publisher page returned HTTP 403 so the numeric thresholds are not cited here — [Semantic Scholar record](https://api.semanticscholar.org/graph/v1/paper/search?query=Time+discrimination+in+a+monotonic+isochronous+sequence)

### Inferences
- Grid arithmetic (computed, not sourced): at 90 bpm a beat is 667 ms, an 8th 333 ms, a 16th 167 ms; at 120 bpm 500/250/125 ms; at 160 bpm 375/188/94 ms. Snapping is unambiguous when timing error < half the grid step, so the error budget is ~83/62/47 ms for 16ths at 90/120/160 bpm and double that for 8ths. Combined Beat This! jitter (~+/-20 ms) plus Basic Pitch onset jitter (~+/-12 ms, plus any systematic latency) stays inside the 16th budget below ~160 bpm only if beat positions are smoothed; above that, 16th-level strum detection should fall back to pattern templates (e.g., D-DU-UDU) rather than per-note snapping.
- Swing and pushed strums (anticipations of ~1/3 beat) will land halfway between straight-16th grid lines; a (4, 3) or (4, 6) divisor set as in music21 plus a swing-ratio test (ratio of long:short 8th within each beat, ~2:1 for triplet swing) is the needed extension; none of the fetched tools implements the ratio test.
- Measuring the systematic Basic-Pitch-vs-beat latency per song (as Coming Undone does) and subtracting it before snapping is cheap and likely removes a constant 10-30 ms bias (inference).
