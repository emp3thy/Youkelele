## Notes per item

### A1 Beat This!

- Install: `pip install beat-this` (PyPI name `beat-this`, import `beat_this`); dev: `pip install https://github.com/CPJKU/beat_this/archive/main.zip`. Version 1.1.0, released 2026-04-14. Licence MIT for code; the maintainer stated in issue #16 (opened 2026-05-28, closed) that the MIT licence also covers the weights.
- Python range: `requires-python >=3` with no upper bound; in practice `torch>=2` sets the floor at 3.10 and torch 2.14.1 ships wheels up to 3.14.
- CPU: the README's `--gpu=-1` forces CPU on the CLI; the Python API `Audio2Beats(checkpoint_path="final0", device="cpu", float16=False, dbn=False)` defaults to CPU. PR #14 (merged 2026-02-02) guards `autocast` on unsupported devices, so CPU and MPS are explicitly handled.
- madmom: needed only when `dbn=True` / `--dbn` (`DBNDownBeatTrackingProcessor`); install from git if ever wanted (`pip install git+https://github.com/CPJKU/madmom.git`), PyPI madmom stops at Python 3.9 (issue #9). The spec does not use it.
- Checkpoints: `final0.ckpt` (77.3 MB) from `cloud.cp.jku.at` via `torch.hub.load_state_dict_from_url`, cached as `~/.cache/torch/hub/checkpoints/beat_this-final0.ckpt`. Other checkpoints (`final1`, `final2`, `small0` ...) follow the same pattern.
- Windows: no Windows-tagged issue in the tracker. The one real hazard is audio I/O: `beat_this.preprocessing.load_audio` tries `torchaudio.load` first; on torchaudio 2.11 that raises `ImportError: TorchCodec is required for load_with_torchcodec` (torchaudio 2.9+ delegates decoding to TorchCodec, which needs FFmpeg shared libraries; the static-ffmpeg exe does not provide them). The function then falls back to `soundfile.read`, which handles WAV. Keep the ingest stage's "always write 44.1 kHz WAV" rule and do not install torchcodec.
- Measured: model load including download 5.6 s; 30 s click track 1.7 s on CPU, beats at 0.5 s spacing as expected.

### A2 Chord-CNN-LSTM and ChordMini

- Chord-CNN-LSTM (music-x-lab/ISMIR2019-Large-Vocabulary-Chord-Recognition): MIT `LICENSE`; the five ensemble members used by `chord_recognition.py` (`joint_chord_net_ismir_naive_v1.0_reweight(0.0,10.0)_s0..4.best.sdict`, 5.7 MB each) are committed under `cache_data/`, so the spec's "downloaded on first use into a cache folder" is wrong for this model: nothing is downloaded, the repository must be vendored or cloned. Reweighted alternatives are on Google Drive and are not needed.
- Dependencies: `requirements.txt` has only lower bounds (`torch>=1.4.0`, `librosa>=0.7.2`, `numpy>=1.19.2`, `h5py`, `joblib`, `mir_eval`, `pretty_midi`, `pydub`, `pumpp`, `jams`, `scikit_learn`, `matplotlib`, `figures`). Inference imports `torch`, `numpy`, `librosa`, `h5py`, `joblib`; the rest are training-only. No compiled extensions, no Linux-only libraries. The README's note about `torch.bool()` indexing did not bite on torch 2.14.1; what did bite was `np.int` (removed in NumPy 1.24): 10 occurrences in `extractors/xhmm_ismir.py`, `extractors/xhmm_decoder.py` and `results_ismir2017.py`. A `np.int -> int` substitution was enough.
- Inference: `python chord_recognition.py <audio> <out.lab> [submission|ismir2017|full|extended]` loads audio with `librosa.load(..., mono=True)`, computes `librosa.core.hybrid_cqt` (still present in librosa 1.0), runs the five nets (CPU automatic), HMM-decodes and writes a tab-separated `.lab`: `start<TAB>end<TAB>label`. Labels are Harte with inversions and sevenths, e.g. the synthetic C-G-Am-F loop came back as `C:maj`, `G:maj`, `A:min/b3`, `F:maj`, with a leading `N`. The `submission` dictionary has 24 qualities per root plus `N` (`maj, min, aug, dim, maj7, 7, min7, hdim7, dim7, maj9, 9, min9, 11, 13, sus4, sus2, sus4(b7), maj/3, maj/5, min/b3, min/5, maj/2, maj/b7, min/2, min/b7`). Runtime 9 s for a 16 s clip on CPU with all five models, so about 2 to 3 minutes for a 4-minute song.
- ChordMini (ptnghia-j/ChordMini): MIT; checkpoints are plain files in `checkpoints/` (no LFS): `btc_model_best.pth` 35.9 MB, `2e1d_model_best.pth` 27.5 MB, `btc_model_large_voca.pt` 12.2 MB (the original BTC teacher, MIT from jayg996/BTC-ISMIR19). `requirements.txt` is fully pinned (`torch==2.9.1`, `numpy==1.26.4`, `librosa==0.10.1`, `scipy==1.13.1`, `setuptools==80.9.0`); those pins imply Python <= 3.12 and conflict with audio-separator (`numpy>=2`) and librosa 1.0. Device selection is `cuda > mps > cpu` with no flag; it printed "Using device: cpu" here. Run on the unpinned stack (torch 2.14.1, numpy 2.5.3, librosa 1.0.0) it worked: `python src/evaluation/test.py --model_type ChordNet --checkpoint checkpoints/2e1d_model_best.pth --config config/ChordMini.yaml --audio_dir <file> --save_dir <dir>` wrote `<stem>.lab` with space-separated `start end label` and labels `C`, `G`, `A:min`, `F`, `N` (majors as bare roots, which `mir_eval.chord.split` accepts). 1.4 s for the 16 s clip.
- Recommendation: keep Chord-CNN-LSTM as the primary (as the spec says) because it is MIT, tiny, CPU-automatic, dependency-light with lower bounds only, emits inversions and `sus4(b7)` that the arrange stage can use, and was MIREX-2025-competitive. Offer ChordMini as `--chord-model chordmini` since it runs on the same stack when its pins are ignored and is faster; its label vocabulary (BTC large-voca, 170 classes, no inversions) is a subset of what the harmony stage needs. Both repos should be vendored with their LICENSE files; record checkpoint SHA-256 in the manifest.

### A3 python-audio-separator

- Install for this machine: `pip install "audio-separator[cpu]"` (adds `onnxruntime`); `[gpu]` is CUDA-only; `[dml]` is the experimental DirectML path for Intel/AMD on Windows. Python `>=3.10,!=3.14.1`; 3.12 confirmed by resolution and import.
- Two defects to work around in our code: (1) `audioread` is imported unconditionally but not declared; with librosa 1.0 (which no longer depends on audioread) the import fails. Declaring `audioread` ourselves fixes it. (2) `Separator.__init__` shells out to `ffmpeg -version` and raises `FileNotFoundError` when ffmpeg is not on `PATH`; `static_ffmpeg.add_paths()` before construction satisfies it. No issue is filed for either in the tracker as of today.
- Model string: `load_model(model_filename="htdemucs_6s.yaml")`; audio-separator downloads the YAML from `TRvlvr/model_repo` and the weights `5c90dfd2-34c22ccb.th` from Meta's `dl.fbaipublicfiles.com` into `model_file_dir`. The Demucs README calls the 6-stem model "experimental" with "okay quality for guitar, but a lot of bleeding and artifacts for the piano source".
- CPU runtime: no published audio-separator figure for `htdemucs_6s`. Demucs README: about 1.5 times the track duration on CPU. Measured on this machine (Core Ultra 9 285H, CPU, torch 2.14.1+cpu, 42 chunks): 247.7 s for a 240 s stereo 44.1 kHz WAV, i.e. about 1.0x real time for all six stems, plus 6.5 s to download and load the model. Output files are named `<stem>_(Guitar)_htdemucs_6s.wav` etc. in `output_dir`; the separate stage must rename them to the spec's `stems/guitar.wav` (or pass `custom_output_names`).
- Licence: Demucs code is MIT; the README has no separate statement for the weights, which Meta hosts; the research notes already treat this as MIT. Spec wording "htdemucs_6s (MIT)" stands, with the caveat recorded in the manifest text.

### A4 yt-dlp, Deno, ffmpeg

- yt-dlp 2026.08.19 is the current release; Python >= 3.10. YouTube needs `yt-dlp-ejs` (pinned `==0.8.0` by the `default` extra) plus a JavaScript runtime; Deno is the only runtime enabled by default and is located on `PATH` (or next to `yt-dlp.exe`, or via `--js-runtimes deno:<path>`). Without a runtime, YouTube support is deprecated and limited.
- Pip-only runtime: the `deno` PyPI package (maintained by the Deno authors, MIT, 2.9.7 on 2026-09-17) ships the Windows binary as a `win_amd64` wheel, installs a `deno` console script and exposes `deno.find_deno_bin()`. yt-dlp's own `pyproject.toml` has a `deno` extra (`deno>=2.6.6`) and a `pin-deno` extra (`deno==2.9.5`), so `yt-dlp[default,deno]` is the sanctioned spelling. Verified: yt-dlp found `deno-2.9.7` in the venv and solved YouTube's JS challenge with it.
- ffmpeg from pip: `static-ffmpeg` 3.0 downloads ffmpeg 8.0 and ffprobe on first `add_paths()` into its own `site-packages` folder (Windows x64 build from gyan.dev "essentials", which is a GPL build; it is downloaded by the user at run time, not redistributed by us). yt-dlp accepted it through `--ffmpeg-location`. Alternatives `imageio-ffmpeg` (no ffprobe) and `ffmpeg-binaries` (has ffprobe) also exist; librosa and soundfile read WAV through libsndfile and need no ffmpeg at all.
- Recipe for the spec: dependencies `yt-dlp[default,deno]`, `static-ffmpeg`; at start-up `static_ffmpeg.add_paths()`, then run yt-dlp with `ffmpeg_location=<dir>` and `js_runtimes` pointing at `deno.find_deno_bin()`, and convert with the same ffmpeg. Put "ffmpeg binaries not yet downloaded" into the preflight that reports missing tools before any work starts.

### A5 mir_eval and librosa

- mir_eval 0.8.2 (2025-02-25) has no label-to-triad function. `split(label, reduce_extended_chords=True)` returns `[root, quality, scale_degrees, bass]` and only folds 9/11/13 qualities into their 7th base (`min11 -> ('min7', {'9','11'})`); `min7` and `hdim7` stay as they are. The reduction the spec needs is: split, `quality_to_bitmap(quality)`, compare the first eight semitones with the bitmaps of `maj, min, dim, aug, sus4, sus2`, `join(root, match)`; drop the bass. Verified mapping: `C#:min7 -> C#:min`, `G:7 -> G:maj`, `F:maj7 -> F:maj`, `A:hdim7 -> A:dim`, `D:sus4(b7) -> D:sus4`, `E:dim7 -> E:dim`, `C:maj/5 -> C:maj`, `C:min9 -> C:min`, `C:maj6 -> C:maj`, `C:minmaj7 -> C:min`, `C:13 -> C:maj`, `N -> N`, `X -> X`. mir_eval's `QUALITIES` lacks `aug7`, so guard with `InvalidChordException`. Harte syntax is the grammar mir_eval parses.
- librosa 1.0.0 (2026-08-11) requires Python >= 3.12, drops the audioread backend, and keeps the full `librosa.segment` module; the Laplacian example moved to `auto_tutorials/03-advanced/plot_segmentation.html`. The example's chain (`cqt -> beat_track -> util.sync -> feature.stack_memory -> segment.recurrence_matrix -> segment.timelag_filter(median_filter) -> csgraph.laplacian -> eigh -> KMeans`) ran locally on 1.0.0.

### A6 Playwright

- `page.pdf()` is Chromium-only (it is the Chromium DevTools print path); the Python docs describe print-media rendering, `emulate_media`, and the `format` / `margin` / `print_background` / `prefer_css_page_size` options. `file://` navigation needs no flag, and external `<script src>`, `<link>` stylesheets and web fonts load; wait with `wait_until='networkidle'` then `page.evaluate('document.fonts.ready')`.
- Origin restrictions on `file://` do matter for alphaTab: `fetch()` and `Worker()` from a `file://` page fail in Chromium 153. alphaTab's default is to render in a worker. Setting `core.useWorkers: false` renders synchronously on the main thread; the Bravura font is loaded through generated CSS from `fontDirectory` (default `${AlphaTabScriptFolder}/font/`), which works on `file://`. `--allow-file-access-from-files` additionally lets workers start from `file://` but does not make `fetch()` work. The rendered page in `07_render/sheet.html` should therefore inline the alphaTex and the chord data, and the PDF step should wait for alphaTab's `renderFinished` event rather than for network idle.
- Browser reuse: Playwright maps each release to a browser revision; 1.63.0 = `chromium-1243` / `chromium_headless_shell-1243` (Chromium 153.0.8010.12), both already present in `C:\Users\gethi\AppData\Local\ms-playwright`, and 1.63.0 launched them without any install step. `chromium-1247` is Chromium 155.0.8059.12 from a newer pre-release toolchain and will be ignored (and may be garbage-collected by Playwright unless `PLAYWRIGHT_SKIP_BROWSER_GC=1`). Pin `playwright==1.63.0`; for other machines or after an upgrade run `playwright install chromium` (or `--only-shell`) in the preflight.

### A7 PyTorch

- torch 2.14.1 (uploaded 2026-09-30) has `cp312` Windows wheels on PyPI, and the PyPI Windows build is the CPU build (`2.14.1+cpu`), so `uv add torch` with no custom index is enough; `https://download.pytorch.org/whl/cpu` is equivalent. torchaudio 2.11.0 pairs with it and resolves fine, but its `load`/`save` require TorchCodec (A1).
- Intel XPU: the 2.14 docs list Windows 11 and Arrow Lake-H integrated Arc as supported through `--index-url https://download.pytorch.org/whl/xpu` plus the Intel driver, so it is possible in principle. None of the three model wrappers would use it without code changes (audio-separator: cuda/mps/directml/cpu; ChordMini and ISMIR2019: cuda or cpu; Beat This!: any device string). Recommend ignoring XPU and DirectML in v1 and keeping CPU as the only path; the spec's "all inference runs on CPU" stands.

### A8 Python 3.12

- Full resolution on 3.12 for Windows succeeded with uv 0.12.22 and every package imported in a 3.12.15 venv. No package pins `<3.12`. Two constraints pin from the other side: librosa 1.0 requires `>=3.12`, and ChordMini's `numpy==1.26.4` has no 3.13 wheels. So the spec's "3.10 to 3.12" becomes "3.12 exactly"; `requires-python = "==3.12.*"` in `pyproject.toml`.
- The only runtime breakage found in the set was audio-separator's undeclared `audioread` import (A3), which is a librosa-1.0 consequence rather than a Python-3.12 one.
